# 多边多云边云架构 · 应用视角版（embedding_only 模式）

> 面向有推理引擎基础的读者：术语照用（prefill/decode、prefix cache、block、调度），
> 但叙述停在**架构行为层**——讲清"系统怎么运转"，不涉及数据结构、协议字段等实现细节。
> 只覆盖两个主题：**多边多云场景** 与 **KV cache 管理**。
> 开发级设计见《multi_edge_cloud_design_embedding_only.md》。

---

## 1. 一句话概括

现状是一边一云强绑定；目标架构是**边池化、云池化，外加一个中央调度器**：
每个请求在 prefill 前由中央调度器完成一次路由（综合 prefix cache 命中与各云负载），
选定后该请求的 decode 全程复用这朵云，不再变更。

---

## 2. 角色与分工

```
                 ┌────────────────────┐
                 │     中央调度器       │   只做路由：Route 请求 → 返回目标云
                 │  · GPI（各云 prefix   │   不进数据面、不做逐 token 调度
                 │    cache 全局视图）  │
                 │  · 各云负载视图      │
                 └─────────▲──────────┘
                           │ Route RPC（每请求仅一次）
   ┌───────────┐   ┌───────┴───┐   ┌───────────┐
   │  Edge 0   │   │  Edge 1   │ … │  Edge N   │   边侧：embedding + final norm/lm_head
   └─────┬─────┘   └─────┬─────┘   └─────┬─────┘   + 采样；**无 transformer 层、无 KV**
         └───────────────┼───────────────┘
              hidden states（HCCL P2P，按 pair 互联）
   ┌─────────────────────┴──────────────────────┐
   │   Cloud 0      Cloud 1     …     Cloud M    │   云侧：全模型层 + 全部 KV cache（自管）
   └─────────────────────────────────────────────┘
```

- **边侧（embedding_only）**：只负责 embedding、final norm、lm_head 与采样。
  无 transformer 层、不持有任何 KV——**边是无状态的**，宕机重启无缓存损失。
- **云侧**：执行全部 transformer 层，持有全部 KV cache 并**自行管理**（分配、命中、驱逐、
  卸载、重算），多个边的请求共享同一朵云的块池。
- **中央调度器**：维护两份全局视图——GPI（各云缓存了哪些 prefix 的索引）与负载视图
  （各云 KV 余量、队列深度等心跳指标），仅用于回答"这个请求路由到哪朵云"。

---

## 3. 一个请求的完整生命周期

以一个 200 token 的请求为例。

**① 路由（每请求仅一次）**

边对 prompt 计算 block 级哈希（纯 CPU，不跑模型），携带 prompt 长度向中央发起 Route。
中央对每个候选云做最长前缀匹配估算命中，再结合负载打分（余量、队列深度、近期抢占降权），
同分按首块哈希一致性哈希——让相同 prefix 的请求天然聚集到同一朵云，命中率随时间上升。
决策后中央在所选云上为命中的 prefix 块下一个**租约（lease）**：短暂保留这些块不被驱逐，
防止"路由时命中、到达时已被逐"。租约是优化而非强一致保证——失效的最坏后果只是云多算一段。

**② 全量下发**

边将**全量 200 token** 的 embedding 与 token ids 发往目标云，不按估算命中截断。原因：
云自管 KV 需要全量 token 序列在本地重建哈希链；全量到达保证"实命中低于预期"时输入依然
齐备；且 embedding 是查表操作，边侧成本可忽略。代价是 e2c 带宽与 prompt 长度成正比。

**③ 云侧准入与执行**

云收到后先做准入：逐边配额、全局在飞上限、KV 余量核算，不满足则回 NACK（边重新路由，
中央临时降低该云权重）。通过后做**权威命中判定**——以云本地块池为准，路由期的估算只是
参考。本例命中 180，云只对后 20 token 做前向：新位置的 attention 读取缓存中前 180 个位置
的 K/V，新算的 K/V 写入新分配的 block。

**④ 首 token 回传**

c2e 只回传**末位置的 hidden states**——em 模式的边尾是 position-wise 的 norm + lm_head，
无需任何历史位置的输出。回传负载与 prompt 长度解耦。边完成采样，输出首 token。

**⑤ decode 循环（复用路由）**

之后每个 decode step：边直发该云（查本地路由表，不再询问中央），云做增量分配并执行，
回传末位置 hidden，边采样。直到结束。

**⑥ 释放**

完成或取消时边发显式 FIN，云释放该请求的 block——但不删除其哈希映射，
块转入**空闲 prefix 缓存**，等待后续同 prefix 请求命中。

## 4. 云侧如何同时处理多个边的调度诉求

**单队列、来源不可知。** 云不为每个边设独立队列，所有边发来的调度单元进入同一张全局队列，
出队只取决于两条：**优先级档**（decode 类优先于 prefill 类——保障在生成请求的时延）与
**到达序号**。云在调度时甚至不需要知道一个单元来自哪条边；只有三个时刻才解析来源：
执行时选择对应的数据面通道、回传时定向、以及清理失联边的残留时。

**唯一的顺序硬约束：同一边的请求严格按到达顺序执行。** 因为每条边内部的流水线状态机
（prefill 分段配对、decode/draft 交替）都假设对端按发送序消费。跨边可以按优先级穿插，
同边内绝不乱序。

**过载防护收敛在准入口。** 每条边有在飞配额（可配权重），超限的新 prefill 会被 NACK 或排队，
不会挤占其他边的份额；叠加全局限额与 KV 余量硬校验，保护云整体不过载。
被 NACK 的请求由边重新向中央询价，自动流向更空闲的云。

## 5. KV cache 管理

### 5.1 缓存什么、收益多大

云缓存每个 token 在每层的 K/V 中间结果；同 prefix 的新请求直接跳过已缓存部分的前向计算。
以 200 token 请求为例：

| 云端命中长度 | 实际需要前向 | 算力节省 |
|---|---|---|
| 0 | 200 token | 0% |
| 180 | 20 token | 90% |
| 200（全命中） | 1 token | ≈99% |

两点说明：
- **全命中也至少要算最后 1 个 token**——缓存里是各层的 K/V，不是各层的输出 hidden；
  产出首 token 需要末位置的 hidden，必须现算。（实现上命中按 block 粒度向下对齐。）
- **边侧行为与命中率无关**：embedding 全量发、采样照常做；命中率的全部价值体现在云侧算力。

### 5.2 跨边共享

块池归云自管的直接红利：**任一边算过的 prefix，其他边命中即用**，无需任何额外机制。
典型受益场景：系统 prompt（全集群算一次）、多轮对话（同会话聚集同云）、热点文档。
中央的一致性哈希路由会持续放大这个红利。

### 5.3 保留与过期

- **活跃请求的块**：不可驱逐。
- **租约保护的块**（路由后、请求到达前的短暂窗口）：不可驱逐。
- **空闲 prefix 块**：默认纯 LRU——命中即刷新热度，最久未命中的优先被淘汰，
  无需人工规则。仅在流量有明显会话周期时可选配 TTL 做提前清理。

驱逐决策完全在云本地，中央不做逐块干预。

### 5.4 缓存满载的四级处置（代价从低到高）

1. **准入控制**：路由期按估算足迹只送往余量充足的云 + 云侧接单复核 NACK。
   绝大多数压力在此消化。
2. **空闲缓存驱逐**：淘汰无主的冷 prefix 块。零即时代价，仅未来请求可能 miss。
3. **offload 到主机内存**：把暂不活跃请求的 KV 异步搬到 host DDR（期间暂停该请求的调度），
   需要时预取回来。搬运与计算重叠，不打断正常服务。
4. **重算（兜底）**：清退某请求的缓存令其重来。em 模式下重算代价很低——边重发 embedding
   即可（边侧无 transformer 层，不涉及边侧重算）。防雪崩纪律：高低水位滞后启动/停止、
   单云频次上限、发生过重算的云被中央暂时降权。

### 5.5 与中央的同步：只作路由参考

云将缓存的增删（insert/evict）攒批上报中央，构成 GPI；另有周期性心跳携带负载指标与
摘要信息用于对账。核心原则：

> **GPI 与中央存在同步延迟，因此它只参与"路由到哪朵云"的推荐，绝不参与任何实际的
> 资源分配与命中判定——后者唯一权威是云本地。**

视图与现实的偏差只会导致"路线次优"或"云多算一段"，永远不会产生正确性问题。
这是整个架构能容忍最终一致性的关键设计立场。

## 6. 异常场景速览

| 场景 | 行为 |
|---|---|
| 边宕机 | 云超时后清理该边的在途请求，缓存转公共空闲池；**边无状态，重启零损失** |
| 云宕机 | 中央广播，各边将相关请求重路由；em 下重算只需重发 embedding，是代价最低的故障切换 |
| 中央宕机 | 各边退化为本地默认路由继续工作；中央无持久化状态，恢复后自动重建视图，可热备 |
| 消息丢失/重复 | 每调度单元有唯一凭证，重复丢弃、丢失超时重发 |
| 请求中途取消 | FIN 通知云；在执行单元正常收尾后释放，缓存照常保留可复用 |

---

## 7. 五个关键设计取舍

1. **全量发送**——用 e2c 带宽换流程的简单与零缺料风险（截断优化留有备案）。
2. **GPI 最终一致**——用对账成本换路由低延迟；偏差只影响路线优劣，永不影响正确性。
3. **云侧单队列、来源不可知**——调度逻辑极简；公平性由准入口配额承担，而非复杂的调度算法。
4. **全云同一时刻只允许一个切片化 prefill**——用部分并行度换执行状态单例的内存与安全。
5. **KV 完全云自管**——最大的架构改动，换来跨边 prefix 共享与清晰的故障责任边界。
