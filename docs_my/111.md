三、 主流程

和多实例的关系、prefix命中使用hash

1.单个请求处理流程：
- 阶段一：边侧请求接收与路由查询
    请求到达边 E0 后，边做 tokenize 并按 vllm 原生链式哈希算出整段 prompt 的 block_hashes。随后边向中央调度器发起一次 Route RPC，携带block_hashes、prompt长度和优先级。中央调度器对每个候选云做最长前缀匹配（估算该云能省多少算力），结合路由算法对每个云侧打分。决策后把 {cloud_id, est_hit, lease_id} 返回给边。边在本地路由表记下req_id → (cloud_id, lease_id)。这就是这个请求整个生命周期里唯一一次路由决策。
- 阶段二：prefill下发
    边做 embedding（首x尾x场景还有前几层），将数据发往cloud，因为云自管 KV 需要全量 token ids 在本地重建链式哈希，需全量发送保证"云实命中低于预期"时输入依然齐备。云需要标识来源边，入口适配层把 req_id/head_token 包装成云内全局唯一键（`e{edge_id}-` 前缀，边完全不感知，回传时再剥离）。
- 阶段三：首token计算
    云调度器有一个全局队列，暂时按先入先出处理，唯一约束是"同边不可超越"——同一边的段严格按到达序执行。出队时从 req_id 解析 edge_id，将中间结果回给对应的边侧。边侧受到中间结果后做norm、采样等操作，生成首个token。
- 阶段四：decode循环
    后续边每步从本地路由表查到 cloud id，直发 DF 段。cloud 收到后查请求注册表、做增长分配，执行中间层计算，回传中间结果，边侧做尾段处理。这个循环直到 EOS 或达到长度上限。
- 阶段五：请求结束
    请求完成或客户端 abort 时，边发显式 FIN 控制消息（独立通道、重传+幂等）。云收到 FIN：若该请求仍在排队，直接弹出——块转空闲 prefix 缓存（hash 映射保留，可被其他任何边的同前缀请求命中）；若正在处理，做一个标记，处理后结果丢弃不回传，再释放资源。边侧删除本地路由记录。

2.多边请求处理：
- 云不为每个边设独立队列，所有边发来的调度请求进入同一个全局队列，出队只取决于两条：优先级（规则待定，例如d优先p等）与到达顺序。云在调度时不需要知道请求来自哪条边。只有三个时刻需要解析来源：接收时标记来源、回传时解析、以及清理失联边的残留。
- 同一边的请求严格按到达顺序执行（当前FIFO队列应该可以保障），每条边内部都假设对端按发送序消费，避免P、D互相死锁。跨边应该可以乱序。
- 云侧的PD穿插场景，不同来源的请求可能会互相穿插，穿插的decode可以来自所有边。
- 层切分：运作方式：slice 0 执行完，把中间结果（hidden/residual、positions、attn metadata、logits indices、spec decode metadata 等）写进一组全局单例字段，如果第二个sliced prefill此时开始切它的slice 0，就会覆盖这组字段，导致状态被破坏，当前已有锁保护。因此这是全云全局单例的，多边的多个p同时也只能有一个能按照层切分处理。
- 提前收 + cloud_prepare_early：req-id在接收时增加edge-id的前缀，保证唯一性，多边存在标识。
- 多边下的NPU-CPU 异步重叠机制：一边一云时边云强同步确定性交替，异步重叠优化（CHER、prepare-early、层切分穿插、 异步采样修正）都建立在"对端下一步可预测"上；多边后云对任一边非确定调度。
- MTP 场景下 DF/DL 与DRF/DRL 严格交替，draft 步共用 DECODE 通道，他边的段可以穿插其间（只延迟不错序，共享 buffer由快照/恢复保护）。但共享的buffer等相关信息存在被覆写的风险。

3.云侧组batch
batch：各边段按req_id前缀分组的连续拼接；算完按段边界切片、按前缀各回各边。
- merge window + 超时：batch需要限制大小和时间，例如一段时间内到的请求组batch，如果这段时间内到的太多，就需要分批组batch，但同一边的请求在全局上顺序需要和到达时保持一致。
- 部分请求提前终止或某个边挂掉时，将相关请求拆出去


四、 kv cache管理

1.边云总体架构：
    首x尾x场景边云各自独立管理kv cache，embedding场景可以把kv cache管理完全放到云侧。此时对于prefix cache场景，embeding模式可以完全按照云侧缓存命中
来计算，因为只有云侧存在kvcache。但是首x尾x场景，需要取边云两端命中的min，因为kv cache存的是K\V，不是hidden。示例场景如下：
- 边 [ABCDE] 云 [ABC]   --   只能复用ABC，后续因为云侧缺失，边侧需要重新算D的hidden，提供给云侧做中间层计算。
- 边 [ABC] 云 [ABCDE]   --   一样的逻辑，云侧也需要重新算D的hidden回给边侧，作为尾段的输入。
- embedding场景，边侧实际上没有kv cache，因此可以完全按照云侧的cache命令来计算。
- 全命中也至少要算最后1个token，产出首token需要末位置的hidden，必须现算。
- 每个云实例中的kv cache都是可以多边共享的，例如E0处理请求后，缓存中存在[ABC]，E1请求到来时如果可以命令这段缓存，是可以直接复用的。

2.每个实例内部的kv cache由各自独立管理，边云之间不需要互相关联。
- 实例内部的管理可以完全复用vllm本身的逻辑，通过引用计数来标记缓存块，空闲队列通过LRU规则控制老化。
- 当前实现中所有kv的管理与分配都由边侧决定，云侧完全被动。因此云侧的调度器中需要增加kv cache的相关管理实现，边侧不再向云侧传递kv相关的信息。例如：
    KVCacheConfig  ---  云侧根据自身情况独立计算，不再需要边云对齐
    block_ids（块表） ---  prefill时云侧本地独立分配维护
    num_computed_tokens  ---  边云要一致
    prefix 命中判定、slot_mapping/positions 等信息的来源均变成云侧本地生成。

3.过期规则：
- 活跃的缓存块（正在使用中）
- 被命中的块，例如当前边侧有一个请求已经命中了这个云的缓存（中央调度器的状态存储），是否需要新增机制，让调度器给云侧发消息预留这个缓存块，这个请求到达前不要被驱逐？
- 空闲队列的缓存块，按照默认的LRU规则老化即可

4.过载处理
- 准入控制：提前根据调度器中的状态存储，估算路由到的云是否资源充足，云侧在接收时如果计算当前kv不足，是排队还是退回该请求让其路由到其他云侧？。
- 空闲prefix驱逐：vllm原生行为（弹出复用即逐），无需新代码。
- 重计算：云释放选中请求的全部块（原生路径）→ `PreemptNotice` → 边标记re-prefill-pending → 下轮重新计算prefill。
