## 〇、模块边界与四层总览

### 0.1 信息范围（以最初定义的五大特性为准）

本模块 = **模型执行 + 数据面**，只管"算"与"传"，**不管任何调度编排**。范围：

1. NPU 上模型的分段执行：边侧首段尾段、云侧中间段
2. 跨边云 hidden tensor 的发送与接收，HeadState suspend/resume，stale request 过滤，采样同步
3. hidden tensor 的压缩与量化，投机 draft 的协调
4. 模型层的切分（make_layers / layer slice）与图编译（CUDA Graph / ACL Graph / ex 选项）
5. 跨边云 KV 传输 connector 的复用/扩展（混合或投机场景）

**不属于本模块**：调度器及全部调度逻辑（打标、head_token 生成、通道分配、draft 链调度、slice 决策——调度组）；中央调度/路由（调度组）；引擎进程框架（引擎组）；**通信组与拓扑初始化**（`init_ascend_model_parallel`、PP 组建立、edge/cloud 角色判定、TCPStore IP 互换——**并行组**，本模块只消费建好的通信组句柄）；KV 池化/落盘（存储方向）。本模块与调度组之间只隔一个**外部依赖接口**（§一），不共护任何调度代码。

**依赖规则（解耦约束）**：
1. **严格向下依赖**：L1→L2→{L3, L4}；下层不得 import 上层；L3 与 L4 互不依赖。
2. L1 对 L2 的调用只经 I1（窄接口：一次 execute 调用 + bundle/marker 数据对象），L1 不读 runner 内部状态。
3. 对调度组只经 D1 契约字段交互。

### 0.3 按请求执行顺序看层级关系

```
阶段0  请求到达【调度组】：调度、打标 PREFILL_FIRST、head_token、通道分配（受 C0 约束）
   │（D1：SchedulerOutput，边内 executor RPC、边云间 ZMQ PRE_OUT）
   ▼
阶段1  边首段
  【L1】_execute_model_edge_head（或共享模型边：execute_model_head_pre → marker）
   │（I1）
   ▼
  【L2】runner 分段执行 segment_a（I2→L3 模型/图）
        首段完成：冻结 _edge_prepare_cache、suspend_head_state
   ◄（I1 返回 IntermediateTensors / bundle）
  【L1】isend hidden（I3→L4）；共享模型边：round 末 per-dp_rank isend + 挂 recv 闭包
       （云侧对称：L1 云入口 → L3 recv → L2 segment_c → L3 isend 回）
   ◄── POST_OUT 回传 PREFILL_LAST（C0 契约：仅 prefill、幂等）
   ▼
阶段2  边尾段
  【L1】_execute_model_edge_tail：recv hidden（I3→L4，无条件收）
   │（I1）
   ▼
  【L2】resume HeadState 校验 → stale 过滤 → fast path → segment_e（I2→L3）
   ◄
  【L2】sample_tokens → 首 token（采样在 runner 层）
   ▼
阶段3  decode 循环：每 token 重复 阶段1-2
       【MTP】调度组按契约插排 DRAFT_FIRST/DRAFT_LAST
        → L1 draft 三入口 → L2 draft runner 三段 → L3 draft patch → L4 draft wire
   ▼
阶段4  结束【调度组传播 finished】→ L1 无条件 recv 消费残留（drain 编排端）
        → L2 空转跳过（drain 计算端）→ L4 通道复位
```

**关系结论**：
1. 每个阶段由调度组发起（D1），L1 编排"先算后传/先收后算"的次序，L2 完成计算与正确性校验，L3/L4 是被交替调用的资源层。
2. **L2 是唯一同时依赖 L3、L4 的层吗？不是**——L1 也调 L4（isend/recv 的发起在 worker 侧）。分工是：L1 决定"何时传"（编排），L2 决定"传什么/算什么"（数据与状态），L4 决定"怎么传"（机制）。
3. 采样在 L2（runner），L1 只见 `sample_tokens` 的调用与结果。
4. 唯一旁路：KV connector 的 scheduler 侧钩子在调度路径上被 vllm 原生基类直接调用（I4），不经 L1/L2——vllm 框架决定的特例。

### 0.4 为什么这样划（划分依据）

- **模块只管"算"与"传"**：调度编排全部外置（调度组），层界画在 vllm 现成的命令对象 `SchedulerOutput` 上。
- **L1/L2 纵向切（编排 vs 计算），不横向切（按部署形态）**：多卡边/云与单卡共享模型边是同一执行语义的两种形态，按形态横切会让 fast path、drain、配对校验等知识在两层各重复一遍，且把 `BatchedModelRunner`→`NPUModelRunner` 的继承关系割裂到两层。纵切后：编排逻辑（分发/round/在途收发）归 L1，计算语义（prepare/forward/采样/状态）归 L2，**两种形态在每一层内共享同一份语义**，继承关系收进同层。
- **接口位置都是代码里已有的抽象边界**：L1/L2 界 = `execute_model_pre`/bundle/marker（worker 与 runner 的现成分工）；L2/L3 界 = `EdgeCloudSegment` callable（编排的计算 vs 被编排的计算）；L2/L4 界 = 传输函数族（传输语义 vs 传输机制）。
- **L3/L4 平级是解耦关键**：模型与传输互无依赖（L3 认 tensor、L4 认 meta），CHER/prepare-early 等重叠优化才成立。
- **质量检验**：可替换性（L3/L4 内部重写，I2/I3 不变则上层无感）；故障域闭合（死锁→契约+L1/L4，算错→L2/L3）；共文件债务最小化（model_runner_v1 仅 L2 执行段/L3 构建段两方共持）。

### 0.5 边云对原生 PP（集中式流水线并行）的复用 — 总览与索引

边云流程本质是在 **vllm 原生集中式 PP 并行**（单机内按层切流水、rank 间传 `IntermediateTensors`）上改造的：把"同机 PP rank"换成"边/云节点"，把"逐 rank 接力"换成"三段往返"，为"跨节点、双方向、多批并发"三个新问题加特化。**各复用点已分散标注在对应层章节内**（【集中式复用】/【集中式复用·增强】注释），索引如下：

| 复用点 | 标注位置 | 复用/增强 |
|---|---|---|
| PP 组 P2P 通信（draft 内嵌直接用原生原语） | L4 §5.2-③、L2 §3.2-⑦ | 增强（免握手 meta/合并/多通道） |
| `PPMissingLayer` 缺层占位 | L3 §4.2-① | 复用 |
| `IntermediateTensors` 容器与 execute_model 数据流签名 | L2 §3.2-② | 复用 |
| `SupportsPP` 模型契约 | L3 §4.2-② | 复用（patch = 补契约） |
| make_layers PP 层切分 → 边云非连续区间 | L3 §4.2-① | 增强 |
| BatchType 原生批型 → 边云枚举扩展 | §一 C0 章首 | 增强 |

## 一、外部依赖接口：调度组契约（C0）

> 本章不是本模块的层，是**对调度组的依赖接口说明**：调度组在调度器中实现下列语义，本模块的执行正确性建立在这些语义之上。条款变更需跨组会签。

> **【集中式复用·背景】**① BatchType 的原生批型（`PURE_PREFILL`/`PURE_DECODE`/`PD_MIX`）是 legacy PP / PD 混合调度的打标，边云的 FIRST/LAST/DRAFT 六个枚举是在同一枚举上的扩展，非边云部署仍走原生批型；② "leader rank 调度、非 leader rank 被动执行"是原生 PP 的调度思想，云侧被动调度是它的边云化（ZMQ 替代进程内广播，实现在调度组/引擎组）。

### 1.2 本模块反向提供的语义（调度组可依赖）

- FIRST 批 `execute_model` 返回占位输出（无 logits）、不采样；LAST 批 `sample_tokens` 才产出 token。
- 任何批的 hidden 回包都会被无条件 recv（drain），调度组无需为死请求做传输层清理。
- 带 `LayerSliceInfo` 的批在 L2 强制 eager 执行（L3 图安全约束）。

## 二、L1 执行编排层（Worker / Executor 侧）

> 一句话：**决定"何时算、何时传"——把契约驱动的一步分发到正确的执行路径，编排计算与传输的次序，跟踪每条通道上还没完成的收发。**

### 2.1 模块简介

L1 是本模块的"入口层"：调度组的 `SchedulerOutput` 经 executor RPC 到达的第一个地方就是这里（`NPUWorker.execute_model` 或共享模型边的 `_dispatch`）。它本身**不算矩阵、不管字节格式**，职责是把每一步执行编排成对 L2（计算）与 L4（传输）的正确调用序列：什么批走哪条路径、发送前要不要先聚合、同一通道上上一笔发完了没有、接收要不要提前挂好。

本层要同时服务两种部署形态，接口形状完全一致：

- **多卡边 / 云**：每个 dp_rank 一个 `NPUWorker` 进程，逐 dp 执行（主路径）；
- **单卡共享模型边**：一个进程内 N 个虚拟 dp_rank worker 共享一份模型，整 round 合并执行（`SharedModelEdgeWorker` + `SharedModelWorkerProc`）。

### 2.2 内部功能构成

**① 执行分发（batch_type 路由）**
`NPUWorker.execute_model`（`VA/worker/worker.py:986`）是本模块所有执行的统一入口，按 batch_type 路由到六类路径：

| batch_type | 入口 | 编排内容 |
|---|---|---|
| PREFILL/DECODE_FIRST | `_execute_model_edge_head`（:1056） | 等通道空闲 → L2 算首段 → L4 发送 → 返回占位输出（无 logits） |
| PREFILL/DECODE_LAST | `_execute_model_edge_tail`（:1146） | L4 先收（无条件）→ L2 算尾段 → 随后由 sample_tokens 产出 token |
| 云侧 FIRST 类 | `_execute_model_cloud`（:1188） | prepare-early → L4 收 → L2 算中段 → L4 发回边 |
| DRAFT_FIRST/LAST | :1438/:1476（+云 :1376） | 同首/尾段骨架，载荷走 draft wire |
| 非边云批型（PD_MIX 等） | 标准路径 | 不经边云通道 |
| 空批 | 直通 | 不产生 marker、不占用通道 |

**② 未完成收发的跟踪（在途管理）**
每条 hidden 通道同一时刻只允许一笔发送未完成：`_record_pp_send_work`（:781）记录每笔 send 的句柄，`_wait_pp_send_work`（:794）在下次使用同一通道前等待完成——防止同通道两笔并发导致 HCCL 数据错序（契约 C3 的执行端）。`_hidden_channel_for`（:1043）按 SO 选择通道。

**③ CHER 提前收（Cloud-side Hidden Early Recv）**
云侧对 PREFILL_FIRST 首发 slice，由云引擎下发 recv-hint（调度组侧，`passive_core.py:645-711`），本层守护线程 `start_early_irecv`（:849）按 head_token 提前挂好 irecv。**效果**：边侧首段算完即发、发完即走（发送不被接收未就绪反压），传输与边首段计算重叠，实测隐藏大部分传输延迟。
**归属说明（为什么 CHER 在 L1 而不在 L4）**：CHER 的本质是"把 recv 的发起时机从批到达时提前到 hint 到达时"——是时机决策而非新传输机制。机制（irecv 原语、stream、buffer）在 L4；但"为哪个 head_token 挂、挂多大、何时挂"需要理解协议语义与批状态，属于 L1 的"何时传"职责。这与 isend 发起在 L1、cloud_prepare_early 发起在 L1（内容在 L2）是同一条划分依据：**L1 管时机，L2/L4 管内容/机制**——若把时机决策下沉 L4，L4 就必须感知 head_token 生命周期与 SO 语义，破坏"资源层不感知语义"的解耦约束。

**④ cloud_prepare_early（云侧预处理重叠）**
云侧入口先调 `cloud_prepare_early`（`model_runner_v1.py:7451`）：把 `_update_states`/`_prepare_inputs` 这类 CPU 侧预处理在 hidden 到达之前做完——hidden 一到即可上 NPU，串行路径缩短一段。

**⑤ SP 序列聚合**
开启 sequence parallel（`cloud_enable_sp`）时，边侧各 SP rank 只持有序列的一片，首段发送前先 `_all_gather_tensor_dict`（:954）聚合成全序列再发云；接收侧的对称处理在 L4（SP chunk 延后）。

**⑥ 共享模型边的 round 编排**
`SharedModelWorkerProc.worker_busy_loop`（`V/v1/executor/shared_model_multiproc_executor.py`）round-robin 轮询 N 个 MQ，`_dispatch`（:630）把 `execute_model` 重定向到入口三件套（`shared_model_edge_worker.py:970/:1023/:1060`），返回 marker（`_BatchedExecuteMarker`/`_FirstRoundMarker`/`_LastRoundMarker`）后 pause；end-of-round 按 marker 类型**三路分组**（FIRST/LAST/非 PD，不可混合），分别驱动：
- 非 PD：Phase A `run_batched_head`（合并 head，→L2）→ per-dp_rank isend + 挂 recv 闭包 → Phase B/C `drain_batched_round`（recv + 合并 tail，→L2）→ `handle_output`
- FIRST：只 head+isend，`handle_output(EMPTY)`，bundle 与 recv 闭包存入**跨 round 缓存** `_pd_head_bundles`/`_pd_recv_closures`
- LAST：弹出跨 round 缓存执行 recv → drain

round 触发条件：MoE 等齐全部 dp_rank（`all(paused)`），非 MoE 每轮循环结束即触发（合并不定数）；空批直通不 pause；legacy `DeferredExecutePostprocess` 走独立 deferred 路径（互不干扰）。

**⑦ leader/follower 初始化编排**
共享模型边内，leader（local_rank=0）做设备初始化、分布式初始化、模型加载、图捕获；follower `bind_to_shared_model`（:819-846）绑定到 leader 的模型。`initialize_from_config` 有全进程屏障（`init_kv_cache` 标志），等齐后统一继续。PP 组布局：rank0=边，rank k+1=云 dp_k 首卡——本层维护虚拟 worker（local_rank=k）到云侧 peer（rank k+1）的路由。

**⑧ drain 编排端**
任何批的回包无条件 recv（契约 C6 的执行起点）：即使请求已死、即使尾段计算将被跳过，传输接收必须先完成，保证通道配对。

### 2.3 关键流程：一次 decode step 的编排时序（主路径）

```
NPUWorker.execute_model(so: DECODE_FIRST)
  _wait_pp_send_work(DECODE 通道)        ← 等上一笔完成
  → L2 execute_model(so) → hidden        ← 算首段
  → L4 edge_cloud_isend(hidden)          ← 记录 send work
  返回占位输出                            ← 不采样
（云侧此时：prepare-early → recv → 算中段 → isend 回）
NPUWorker.execute_model(so: DECODE_LAST)  ← 调度组自发，不等 ack
  → L4 edge_cloud_broadcast_recv          ← 无条件收
  → L2 execute_model(so, intermediate)   ← 算尾段（fast path）
sample_tokens → token
```

### 2.4 涉及文件

| 文件 | 内容 |
|---|---|
| `VA/worker/worker.py` | 分发与执行入口、在途收发跟踪、CHER、SP 聚合 |
| `VA/worker/edge_cloud/shared_model_edge_worker.py` | 虚拟 worker、入口三件套、marker 类 |
| `V/v1/executor/shared_model_multiproc_executor.py` | round 编排、`_dispatch`、跨 round 缓存 |

### 2.5 看护要点

- 无条件 recv（drain 编排端）不可破坏：计算可省、传输不能省。
- round 编排的三路分组（FIRST/LAST/非 PD）不可混合合并；跨 round 缓存在 FIRST→LAST 间不被覆盖（分析文档 §5.3）。
- 等待通道上笔收发完成与通道选择的次序是防死锁第二道防线（第一道在契约 C3-C5）。

## 三、L2 计算执行层（ModelRunner 侧）

> 一句话：**决定"算什么、传什么、状态怎么保"——分段 forward 的全部计算语义与正确性协议的执行端。**

### 3.1 模块简介

L2 以 `NPUModelRunner`（主路径）与其子类 `BatchedModelRunner`（共享模型边）为主体，是本模块体量最大、状态最多的一层。L1 告诉它"这一步算什么"，它负责：把 SchedulerOutput 变成 NPU 输入、调用 L3 的 segment 完成 forward、把中间结果交给 L4、并保管首/尾段之间、slice 之间、draft 步之间的全部执行状态。本模块的**正确性协议（HeadState、stale、drain 计算端、采样修正）的执行侧全部在这里**——L1 只编排，兜底的判断与状态都在这里。

### 3.2 内部功能构成

**① 输入与状态地基**
`input_batch`/`_update_states`/`block_table` 等 vllm-ascend 原生机制（本模块不改动语义，但所有边云路径都建立在之上）；边云特有：`head_token` 作为跨段状态的主键。

**② 分段执行路由**
`_edge_cloud_forward`（`model_runner_v1.py:7660`）按角色与是否有 intermediate_tensors 路由：边首段（segment_a，:7768-7793）、边尾段（segment_e，:7795 起，尾 tail_k 层+norm）、云中段（`_edge_cloud_forward_cloud` :8251，含 MoE 游标重置 `_get_edge_cloud_moe_start_index` :363、切片时选 raw segment eager :8274-8291）。多模态时附带 `mrope_positions`。
**【集中式复用】**段间载荷容器 `IntermediateTensors`（hidden/residual）与 `execute_model(so, intermediate_tensors) → IntermediateTensors` 的数据流签名完全沿用原生 PP——首段等价于"PP 非末 rank 产出中间张量"，尾段等价于"PP 末 rank 消费中间张量出 logits"。

**③ 首段收尾：冻结 + 挂起**
首段 forward 返回前做两件 bookkeeping：
- `_edge_prepare_cache_by_token[head_token]`（:5439-5510）：缓存 attn metadata、logits indices、positions 等 prepare 结果，供尾段 fast path 复用；经 `_freeze_scheduled_state`（:424-505）**递归深拷贝**（tensor/ndarray/dataclass/容器，保持共享别名），防止首/尾段之间的穿插批改写这些 buffer；
- `suspend_head_state`（:7982）：挂起 `HeadState`（:382-391，极简 dataclass：head_token/scheduler_output/req_ids，刻意不存 hidden）到 `_pending_head_states`（:897），重复挂起即报错。

**④ 尾段入口链：校验 → 过滤 → 快路径**
`_resume_and_validate_head_state`（:8002）：pop HeadState，校验 batch_type 配对（PF→PL、DF→DL，:8137）与 req_ids 集合——配对错误直接显式报错（防结果张冠李戴）。
stale 过滤（:4733-4808）：请求在首→尾窗口内完成/abort（不在 `self.requests` 或在 `finished_req_ids`）则：
- 全 stale：记 `[EDGE-TAIL-STALE-DISCARD]`、置 `_tail_segment_discarded`、返回 EMPTY（hidden 已被 L1 无条件 recv，通道配对不破）；`sample_tokens` 短路（:5844-5848）；
- 部分 stale：`_filter_stale_tail_batch`（:8144）按 per-req token 区间 index_select 切 hidden、重写调度字段为存活子集，并 pop 首段缓存强制走正常 prepare（:4806）——活请求不被死请求连坐。
fast path：复用首段缓存跳过 `_update_states` 与 attn metadata 重建；必要时 `_restore_frozen_into_views`（:508）把冻结内容写回图捕获的固定地址（ACL Graph 重放要求地址稳定）。

**⑤ layerwise 续算（切片 prefill 的执行端）**
slice 0 把 hidden/residual、positions、attn metadata、logits indices、spec metadata、num_tokens 等冻结进 `_layerwise_*` 单份字段（:877-892，写入 :5520-5637，同样经 `_freeze_intermediate_tensors` :597-602）；后续 slice 走 `_execute_layerwise_continuation`（:7846-7970）：跳过全部预处理，弹出上片 hidden 续算，打 `_is_layer_slice_continuation` 标记（供 L3 的 GDN conv_state 重置识别）。续算强制 `CUDAGraphMode.NONE`（:7895）。

**⑥ 采样与输出**
采样只在边尾段（token 不出边）：`sample_tokens`（:5735）算 logits→采样→`ModelRunnerOutput`；云侧直接返回 EMPTY（:5828）。spec decode 的拒绝采样修正量（`num_accepted_tokens`/`valid_sampled_token_count`）经 PP irecv 收进云侧 `sample_tokens` 开头并写回 input_batch、做 mamba postprocess（:5748-5826）；`VA/sample/rejection_sampler.py:423-480` 的 tile padding 让边云非图 padding 批与图 padding 批行为一致。

**⑦ draft 计算（特性 3 执行侧）**
- context 管理：`_pending_edge_cloud_draft_contexts[task_id]`（:4103）保存每步的 hidden/positions/已验证 token；`_stash_pending_edge_cloud_draft_context`（:3971）在目标批尾段采样后暂存；
- 三段执行：边首 `_run_edge_cloud_draft_first_segment`（:4275）、云中 `_run_edge_cloud_draft_middle_segment`（:6762，含 `_record_cloud_request_corrections` :6793 从 step-0 SO 读修正量、`_build_edge_cloud_draft_attn_metadata` :6482 补云侧 draft 注意力 metadata）、边尾 `_run_edge_cloud_draft_last_segment`（:4396）；
- token 边算：`_compute_edge_cloud_draft_token_ids`（:4336）argmax 出 draft token（不过边云）；`_validate_edge_cloud_draft_payload_identity`（:4364）按 task_id/step/head_token 校验载荷；
- drain 空转（:4396-4426）：context 无该 task 时跳过计算返回空占位（配合 L1 的无条件 recv）；
- 内嵌路径：`llm_base_proposer.py:2146` 的 `_run_draft_edge_cloud`（num_spec>1 每步一次边云 round-trip；**【集中式复用】**其收发直接调用原生 PP 原语 `get_pp_group().isend_tensor_dict`，未经 L4 的免握手通道）；`_sync_edge_cloud_draft_intermediate_tensors`（:2080）把收到的 tensor 拷入预分配 buffer 保图地址稳定；Eagle3 aux hidden 缓存 `_prepare_eagle3_cloud_hidden_states`（:1639-1683）。

**⑧ 共享模型边的合并计算**
`BatchedModelRunner`（继承 `NPUModelRunner`，`batched_model_runner.py:77`）：
- `execute_model_pre`（:570）：per-dp 预处理产出 `_ExecuteModelBundle`（`execute_model_bundle.py:54`，含 input_ids/positions/inputs_embeds/per-gid attn 上下文）；
- `_get_or_build_merged_attn_ctx`（:1574）：把各 dp 的 attn metadata 合并成一份 `AscendCommonAttentionMetadata` 喂回各 builder（无逐层手工合并）；
- `execute_model_batched_head`（:877）/`execute_model_batched_tail`（:1030）：各一次合并 `_model_forward`/`compute_logits` 替代 dp_size 次小调用；tail 含 decode-first 重排/逆排（`merged_token_perm`）；
- `execute_model_post_batched`（:1276）：按 dp_rank 切片回写各虚拟 worker 状态；
- 全局 KV buffer：各 dp 注册 KVCacheConfig 到类级表，最后注册者分配一块全局 buffer（`_allocate_global_kv_cache_tensors` :351），偏移簿记 `_per_dp_offsets`；`bind_to_shared_model` 让 follower 复用 leader 的模型与 buffer。

**⑨ 与 L4 的 KV 交接**
`initialize_kv_cache` 末尾调 `get_kv_transfer_group().register_kv_caches`（`model_runner_v1.py:9715`；共享模型边 `batched_model_runner.py:314/425`）——L2 提供 KV 显存布局，L4 完成 RDMA 注册。

### 3.3 关键流程：一次边尾段执行的内部步骤链

```
execute_model(so: *_LAST, intermediate_tensors)
  _resume_and_validate_head_state     ← pop + 配对校验（错则显式报错）
  stale 判定                           ← 全 stale → EMPTY 返回（采样短路）
                                       部分 stale → 切 hidden、强制正常 prepare
  fast path                            ← 取 _edge_prepare_cache_by_token
                                       （图模式：_restore_frozen_into_views 写回固定地址）
  _edge_cloud_forward → segment_e      ← I2 调 L3（尾 tail_k 层 + norm）
  compute_logits →（随后 sample_tokens）→ 采样 → ModelRunnerOutput
```

| 文件 | 内容 |
|---|---|
| `VA/worker/model_runner_v1.py` | 分段执行、HeadState/stale/fast path/layerwise/采样/draft 计算（构建与 capture 段归 L3） |
| `VA/worker/edge_cloud/batched_model_runner.py`、`execute_model_bundle.py` | 合并计算与 bundle 数据结构 |
| `VA/worker/npu_input_batch.py`、`VA/worker/block_table.py` | 输入与块表地基（原生机制，本模块不改语义） |

### 3.5 看护要点

- frozen 缓存（`_edge_prepare_cache_by_token`/`_layerwise_*`）的深拷贝与写回是防穿插污染关键；改动需构造穿插场景测试。

- HeadState 只做配对校验，数据面对齐靠通道 + head_token（契约 C2/C3）。
- 本层改基类（prepare/采样）影响两种部署形态，需双路径回归。

## 四、L3 模型切分与图编译层

> 一句话：**特性 4 的全部——模型按层怎么切（静态 make_layers + 动态 layer slice）、切完的段怎么编译加速（npugraph_ex + ACL Graph）。**

### 4.1 模块简介

L3 把"完整模型"变成"可按段加载、按区间执行、可按段加速"的形态，是边云方案成立的地基：边侧显存只装部分层靠它，云侧 P/D 穿插靠它，decode 步的 kernel launch 开销消除也靠它。它对上（L2）只暴露一个窄接口——`EdgeCloudSegment` callable（tensor 进 tensor 出，支持 slice kwargs），L2 不需要知道里面是几层、有没有图、是不是 eager。

### 4.2 内部功能构成

**① 静态三段切分（加载期）**
- `make_layers` 边云扩展（`V/model_executor/models/utils.py:632-752`）：`is_edge_cloud_pp_mode()` 时按 `_get_edge_cloud_local_indices`（:714-752）只构建本侧层——边 = `[0, head_k) ∪ [N-tail_k, N)`，云 = `[head_k, N-tail_k)`；`head_k == tail_k == 0` 即 embedding_only（边 0 层、云全量）。本地索引位置建真实层（经 offloader `wrap_modules`），其余位置放 `PPMissingLayer`（Identity 占位、无参数）——**模型直接在 NPU 上按段初始化，权重加载自动跳过占位层，无 CPU→NPU 搬运**。
- **【集中式复用·增强】**原生 make_layers 按 pp_rank 切**连续**区间；边云在同一函数内加分支，切"首+尾"**非连续**区间（云侧仍是连续区间）。`PPMissingLayer` 直接复用原生 PP 的缺层占位，语义未改。
- 层范围传递：全局变量 `set_edge_cloud_layer_range`（`V/distributed/parallel_state.py:1378`），由 `_load_model_edge_cloud`（`model_runner_v1.py:1685`）在 `get_model()` 前设置；MTP/EAGLE3 drafter 加载时临时设为 (0,0)（全量在云），加载完恢复（:1822/:1841）。

**② 分段 forward 注入（模型 patch）**
- `VA/patch/models/qwen3_5_edge_cloud.py`：给 `Qwen3_5Model` 及各 `*ForCausalLM`/`*ForConditionalGeneration` 注入 `forward_edge_cloud_segment(start_layer, end_layer, ..., is_first_segment, is_last_segment)`（:36-139）；边界用 `VA/edge_cloud_materialized.py` 的 `make_boundary_tensors/restore_boundary_state/apply_final_norm`（materialized boundary：部分模型只传 hidden 不传 residual，跨段流量减半）；MoE 的 `set_moe_parameters/update_physical_experts_metadata` 改成容忍 `PPMissingLayer` 的版本（:147-274）。
- MTP/draft 三段 patch 见 §七（`qwen3_5_edge_cloud.py:277-411`、`eagle3_edge_cloud.py`）。
- `supports_pp=True` + `make_empty_intermediate_tensors` + 清 `_ModelInfo` 缓存：上游模型/ MTP 未声明 PP 支持时无法被边云加载，patch 补齐。
- **【集中式复用】**上游的 `SupportsPP` 契约（`supports_pp()`、forward 接受 `intermediate_tensors`、`make_empty_intermediate_tensors`）是原生 PP 的模型接口；本层 patch 的本质是**给边云模型补齐这套既有契约**，不是新造机制——这也是新模型接入时工作量集中在 patch 的原因。

**③ patch 体系（注入机制）**
模块级 import 副作用的 monkey-patch + 文档化登记：`VA/patch/__init__.py` 的 `adapt_patch` 应用 platform/worker 类 patch，`VA/__init__.py` 的 `_ensure_global_patch` 保证 engine-core 子进程同样生效；模型 patch 按模型类型条件 import（`VA/platform.py:192`、`model_runner_v1.py:1716/:9464-9468`）。每个 patch 在 `patch/__init__.py` 以编号条目登记 Why/How/Related PR/Future Plan——**上游升级时逐条复核的清单**。

**④ 动态层切分 forward（layer slice）**
`VA/patch/models/qwen_layer_slice.py`：运行时重绑 `Qwen2Model.forward`/`Qwen3NextModel.forward`（Qwen3 继承 Qwen2Model、Qwen3_5Model 继承 Qwen3NextModel，打基类即全覆盖），新增三个 kwargs：
- `layer_slice_start/end`（相对 `self.start_layer` 的 0 基子区间）：`islice(self.layers, exec_start, exec_end)` 只跑该区间；
- `layer_slice_return_intermediate`：最后一个 rank 也强制返回 `IntermediateTensors`（喂下一 slice）。
`*ForCausalLM` 包装类用 `_make_lm_forward` 透传。由 `model_runner_v1.py:9464-9468` 检测到 layer-slice yaml 存在时按需 import。

**⑤ EdgeCloudSegment 与装配管线**
`_load_model_edge_cloud`（:1685-1837）的装配链：
```
模型（已按段构建）
  → _create_segment_callable (:1558)
      EdgeCloudSegment (:302-360)：轻量 nn.Module，内部调模型的
      forward_edge_cloud_segment；extra_layer_kwargs 可动态覆盖层区间
  → _maybe_compile_segment_callable (:1530)
      包 EdgeCloudCompiledSegment（FX 编译优化，见⑥）
  → _wrap_segment_if_needed (:1585)

  → 保留 segment_c_raw（未编译未包图的裸 segment，供切片 eager 路径）
```
边侧建 segment_a + segment_e，云侧建 segment_c。

**⑥ 编译管线（npugraph_ex / "ex 选项"）**
`VA/compilation/edge_cloud_compiler.py` 的 `EdgeCloudCompiledSegment`（:30-193）把裸 segment 接入两级管线第一级：`torch.compile(fullgraph=True, dynamic=True, skip_all_guards)`，backend 为：
- `npugraph_ex_compile`（`compiler_interface.py:149`）：torchair 的 npugraph_ex FX 编译后端，由 `AscendCompilationConfig.enable_npugraph_ex`（`ascend_config.py:607`，默认开）控制——即"ex 选项"；配套 `enable_static_kernel`（:608，静态 shape kernel）；
- fallback `fusion_pass_compile`（:47）：只跑 `GraphFusionPassManager`（`graph_fusion_pass_manager.py:23-79`）的融合 pass（norm_quant/qknorm_rope/allreduce_rms/muls_add/SP）。
`AscendCompiler.compile`（:283-306）分流；`_configure_backend`（:82-146）设置 `force_eager/inplace_pass=False`、torchair `mode="reduce-overhead"`（即 aclgraph 模式）、static kernel 的 sym_range 等。

**⑦ ACL Graph（NPU 的 CUDA Graph）**
- `VA/compilation/acl_graph.py` 的 `ACLGraphWrapper`（:67-260）：capture 用 `torch.npu.NPUGraph()` + `torch.npu.graph(pool=...)`；按 `BatchDescriptor` 缓存 entry；replay 前在 FULL 非 eagle 模式做一次主流同步；capture 后工作区/输出转 weakref 省显存。
- 图参数：`GraphParams`（:416-421，events/workspaces/handles/attn_params 四个 dict），模块级单例 `_graph_params`/`_draft_graph_params`/`_draft_graph_prefill_params`；attention 后端 capture 时 append task handle/event/attn 参数，replay 前由 `update_full_graph_params`（:272-340）在独立 `update_stream` 上更新（支持 `layer_indices` 过滤 attn metadata，`_filter_attn_metadata_for_layers` :342-393，强制层号升序与 capture 时 islice 顺序 1:1 对齐）——update 与 replay 的 CPU 准备重叠，顺序由 capture 时烧入图的 ExternalEvent 保证。
- 边云适配 `acl_graph_edge_cloud.py`：`make_graph_params`（:33-45）给**每个 segment 独立 GraphParams**（共用会互污 task handle/event）；`graph_params_scope(_no_sync)`（:48-97）临时替换模块级 `_graph_params`；`EdgeCloudACLGraphWrapper`（:107-140）持有 segment 专属参数集，`__call__` 内套 scope 后走父类 capture/replay。
- 捕获流程：`capture_model`（`model_runner_v1.py:11052-11133`）复用 `_dummy_run` 循环，capture 前给每个 segment wrapper 各 `make_graph_params` 一份（:11065-11087），并手动清空 `concrete_aclgraph_entries`（:11123-11124，防 profile 残留 entry 让 warmup 走 replay 挂死）。只有 decode 且 `enable_decode_graph` 时用图（:7690-7693）——prefill shape 多变，图收益低。

**⑧ 图与切片的交互（eager 原则与配套修正）**

## 五、L4 数据面传输层

> 一句话：**特性 2 的收发 + 特性 3 的压缩 + 特性 5 的 KV connector——所有跨边云字节怎么搬。**

### 5.1 模块简介

L4 是本模块的"线路层"：hidden tensor 在边云之间的每一次往返、KV 在 P/D 之间的每一次搬运，都经这里的机制完成。它对上（L1/L2）只暴露语义化的收发函数（"发这份 hidden 到云"），对上屏蔽 HCCL 配对、stream 分配、载荷格式、RDMA 注册等全部机制细节；它对下管理通信库（HCCL/RDMA/ZMQ）。设计三原则：**零握手**（元数据预算，不跑 pickle 协商）、**零冗余**（线上只放有效字节）、**配对绝不破裂**（发多少收多少，宁可多收不可丢）。

### 5.2 内部功能构成

**① 通信拓扑（背景知识，初始化为并行组）**
本模块**不拥有**通信组初始化：`init_ascend_model_parallel`（:537-618）、PP 组建立、edge/cloud 角色判定（`V/distributed/parallel_state.py:1362-1371`）、TCPStore IP 互换均属并行组。本层只**消费**建好的组句柄（`get_pp_group()` 等）做收发。理解收发对端所需的拓扑背景：边（1 个 rank，共享模型边时组内 rank0）↔ 云各 dp 首卡（组内 rank k+1）；虚拟 worker k 的对端是组内 rank k+1。
（注意区分：**tensor meta 与通道 stream 的创建保留在本层**——它们是边云数据面自有的初始化（`init_edge_cloud_tensor_meta`，由 worker 初始化时调用），不是通用并行设施。）

**② tensor meta 体系（免握手的关键）**
`init_edge_cloud_tensor_meta`（:382-480）在初始化时按 hidden_size/dtype/has_residual/hc_mult/mode 预计算 **e2c（边→云）、c2e（云→边）两套 `EdgeCloudTensorMeta`**（:139-145）：每个 tensor 的 key、形状、dtype、是否参与合并、split_sizes。收发双方各自从 SchedulerOutput + config 本地推导同一套形状，**省去通用实现里每次发送前的 pickle+Gloo 元数据往返**——对 decode 这种小 payload 步是数量级的相对收益。meta 构建时同时判定 merge 可行性（hidden 与 residual 同 dtype/同非尾维形状才可合并）。

**③ 发送路径**
`edge_cloud_isend_tensor_dict`（:1159，同步版 `edge_cloud_send_tensor_dict` :1610）：按 `num_tokens` 切片去掉 padding（图捕获要求 padded shape，线上只发有效部分）→ 按 meta 校验 key 集合与形状 → merge 时沿 dim=-1 cat 成单 buffer 一次 isend（:1269-1322）→ 异构 tensor（int64 `mrope_positions` 等）排除合并单独 isend → 返回 work 句柄给 L1 做在途跟踪。
**【集中式复用·增强】**底层传输是原生 PP 组的 HCCL P2P（与 `get_pp_group().isend_tensor_dict` 同一机制），本层在其上加了三个边云特化：免握手 meta、合并 payload、多通道多 stream。

**④ 接收路径**
`edge_cloud_broadcast_recv`（:1749）：按本地 meta + `total_num_scheduled_tokens` 预分配 buffer → HCCL recv（共享模型拓扑显式 `src=0`，:1279）→ **TP 组内 broadcast**（云侧 TP>1 时只有首卡与边通信，其余卡等广播，省边云连接数）→ merged buffer 按 split_sizes narrow 切回 dict（`_split_merged_buffer_into_dict` :1383-1412）→ SP 场景的 chunk 切片延后到 postprocess（与 L1 的 all_gather 对称）。
**【集中式复用】**TP 组内 broadcast 沿用原生 PP 的接收思想：PP 中只有首 rank 与上游通信、其余 rank 等广播——边云把"上游"换成了边节点，机制未改。

**⑤ 通道与流（防死锁的物理基础）**
- 通道池：`HiddenChannelType`（`V/v1/core/sched/output.py:30`，PREFILL_1..N / DECODE 池），prefill 与 decode 各有独立通道，构成双通道流水（防大 payload 队头阻塞）。
- 每通道独立 NPU stream（:41-100，注释含双向流水防死锁说明）：同一 stream 上收发串行化会形成双向等待，独立 stream 让边发云收、云发边收并行。
- 通道预热（`VLLM_ASCEND_EDGE_CLOUD_CHANNEL_WARMUP`，默认开）：HCCL P2P 首用是 rendezvous 式的，若首用发生在 DRAFT_FIRST 插队等非常规时序，两端 rendezvous 错位即死锁；启动时全部通道预热消除首用不确定性。

**⑥ 载荷压缩四件套（结构性，零精度损失）**
| 手段 | 位置 | 效果 |
|---|---|---|
| merge_payload 合并发送 | :254-379（meta 判定）/:1269-1322（cat）/:1383-1412（拆分） | hidden+residual 一次 isend，省一次 HCCL 协议 RTT；env `VLLM_ASCEND_EDGE_CLOUD_MERGE_PAYLOAD` 默认开 |
| embedding_only 省 residual | :382-480 | 边不跑层时 e2c 的 residual 恒为零，剔除线上载荷、接收端 zero-fill，e2c 带宽减半 |
| materialize_residual_boundary | `VA/edge_cloud_materialized.py:52` | 分段边界合并 hidden+residual，双向只传 hidden（适用 qwen3_5/minimax_m2/glm_moe_dsa/kimi_k2），收益最大 |
| draft 专用 wire schema | :181-251（`ScheduledDraftTensorMeta`）/:1627/:1994/:2075 | 每个 draft 步只传最小集合：Eagle3 step-0 只发 input_embeds（hidden 置空壳）、MTP 只发 hidden、云回传不传 residual |

**为什么不做数值量化**：hidden 动态范围层间不稳定，fp8/int8 量化误差经云侧数十层放大影响精度，且 quant/dequant kernel 本身吃延迟；`hidden_dtype` 配置（`ascend_config.py:954`）是预留未消费项。

**⑦ KV connector：注册与传输机制**
**【集中式复用】**connector 框架本身是 vllm 为 PD 分离设计的原生机制（`KVConnectorBase_V1` 的 scheduler 四钩子 + worker 六钩子契约），特性 5 的"复用"即指此——本层按既有契约实现，扩展只在混合模型/draft KV/异构拓扑。
- 注册（worker 侧 `register_kv_caches`，`mooncake_connector.py:2275`）：`kv_group2layeridx`（:2122，把 vllm KV group 细分为 Mooncake 传输组，mtp/eagle 层重编到 total_layers 之后）→ 逐层记录 base_addr/block_len/block_stride → 按底层 storage 合并注册区间（规避 HCCL 每进程 region 上限）+ 2M 对齐校验 → `register_buffer` → 构造 `MooncakeAgentMetadata`（:96，te_rpc_port/各层地址表/handshake_port）。
- 控制面：ZMQ side-channel——发送侧 ROUTER 响应 `GET_META_MSG`（回传地址表）与 `DONE_RECVING_MSG`（收 ACK 后记账，`KVCacheTaskTracker` :166-243 延迟释放/超时回收，防"块已复用、数据被覆盖"的脏读）。
- 数据面：D 侧主动 RDMA 拉取（`batch_transfer_sync_read`），按需重排格式（TP 切头 `_cat_kv_cache` :1264、ND→NZ `_nz_kv_cache` :1290）。
- **混合模型扩展**（特性 5 的"混合"）：Mamba 状态块（`_append_mamba_transfer_meta` :1054）、SWA 滑窗裁剪（`_get_swa_transfer_block_ids` :1678）、压缩 KV（compress_ratio）、SFA/DCP replicated indexer（:3244）；P 侧截掉最后一个 prompt token（`_truncate_request_for_prefill` :1701，让 D 侧重算末 token 得正确 Mamba 状态）。
- **异构拓扑**：P/D TP 不等按 KV head 比例拉取（:1998-2003）、PP 分层（`get_prefill_pp_indices` :3694）、PCP/DCP 分片（`_get_cp_shard_pulls` :3003）、多节点 meta 映射（:1884）。
- **draft/投机扩展**（特性 5 的"投机"）：draft 层编组（:533-545，MTP 多层共享一层 KV 只传一次；:2113-2147 draft 层 KV head 数与层号重编）、`num_speculative_tokens` 偏移（:842，Mamba 组）、MTP extra blocks 裁剪（:1653-1676）。
- **量化传输**：`enable_kv_quant`/`enable_c8_quant` 的 int8 KV 传输带宽减半；**不兼容约束**：producer bf16 / consumer int8 KV 的 C8 量化与 Mooncake 传输存在字节重解释问题，不可组合（`ascend_config.py:368`）。
- 接入点：`model_runner_v1.py:9715`（主路径）、`batched_model_runner.py:314/425`（共享模型边全局 buffer，各 dp 块拼一块再注册）。connector 通用架构演进、metaserver、layerwise 推送、池化落盘**不在本层**（§0.1）。

**⑧ 逐层 save 钩子（接口点）**
各 attention 后端算完一层后调 `maybe_save_kv_layer_to_connector`（`VA/attention/utils.py:442`；调用点 mla_v1.py:1814、sfa_v1.py:1929、dsa_v1.py:1736、dsa_cp.py:1271）——这是 layerwise 逐层传输（存储方向）的触发点，本层只保证钩子位置与 KV 布局正确。

### 5.3 关键流程：一次 hidden 发送的完整路径

```
L1: edge_cloud_isend_tensor_dict(hidden_dict, channel, dst)
  → 按 num_tokens 去 padding
  → meta 校验 key/形状（初始化期预算，无握手）
  → merge：hidden+residual cat 成单 buffer（一次 isend）
  → 异构 tensor（mrope）单独 isend
  → HCCL isend（channel 专属 stream）
  → 返回 work 句柄 → L1 记录在途
对端: edge_cloud_broadcast_recv
  → 预分配 → recv → TP broadcast → narrow 拆回 dict
```

**配置建议**：
- **4 人（推荐）**：L1/L2/L3/L4 各 1 人；L1 兼契约 C0 接口人（编排层最懂配对时序），**且 L1 看护人兼任 L2 副手**（L2 负载为 L1 的约 1.8 倍，见 §8.4，需要分流）。
- **5 人**：L2 拆两人——L2a 主路径计算（分段执行/fast path/HeadState/stale/采样）与 L2b 共享模型边计算 + draft 计算。
- **3 人**：L1+L4 合 1 人（编排与传输的配对知识同源，合计 ~4800 活跃行）、L2×1、L3×1；此配置下 L2 是瓶颈，MTP 大改期需临时支援。
- 互备关系：L1↔L2（两种部署形态）、L2↔L3（model_runner_v1 共文件区）、L1↔L4（配对/死锁链）。

### 8.3 划分质量自评（层级清晰度与负载均衡）

**层级清晰度：四方干净，一处已知债务。** L1↔L2（I1 窄接口：execute 调用 + bundle/marker）、L2↔L4（传输函数族）、L3↔L4（平级无依赖）都清楚；唯一债务仍是 **`model_runner_v1.py`（11312 行）由 L2（执行段 ~2290 行）与 L3（构建/capture 段 ~485 行）两方共持**（纵切后已从三方降为两方）。**中期还债方案**：把 `EdgeCloudSegment`/segment 组装/capture 抽到独立文件（如 `worker/edge_cloud/segment_builder.py`），L3 整文件看护。

**负载均衡：量上 L2 约为其他层的 1.5-1.8 倍；复杂度加权后差距更大（L2 ≈ 2-2.5 倍，见 §8.4）。** 这是纵切的结构性结果：正确性协议（HeadState/stale/frozen/draft 状态机/合并重排）全部集中到 L2，使其成为复杂度汇点。L3 行数最少但图编译是隐性知识（不报错只算错），培养周期最长、是四层里唯一单点风险。L4 行数中维护态占一半，活跃负载实际最轻。

**对冲措施**：① **L2 必须配副手**（由 L1 看护人兼，或 5 人配置拆 L2a/L2b）；② L3 设备份（兼职亦可）；③ 契约 C0 接口人按季度在 L1/L2 间轮换；④ 脉冲预案：新模型接入期 L2 支援 L3，MTP 大改按 §七索引跨层组队；⑤ 中期执行 model_runner_v1 拆文件还债。

### 8.4 复杂度视角的负载再评估（纵切后重算）

五个维度打分（●=高 ◐=中 ○=低），并按「工作量指数 = 活跃区段量 × 变化频率 × 复杂度密度」归一化（L2=1.00）：

| 层 | 功能复杂度 | 并发正确性 | 跨组协调 | 知识深度 | 排查强度 | 活跃区段 | 变化频率 | 工作量指数 |
|---|---|---|---|---|---|---|---|---|
| L1 执行编排 | ◐ round/三路分组状态机 | ● 在途收发/跨 round 缓存 | ● 契约 C0 接口人 | ◐ | ◐ | ~2900 | 中-高 | **0.45** |
| L2 计算执行 | ● 多路径+fast path+stale+draft 状态机+合并重排 | ● frozen 缓存/重排配对 | ◐ | ◐ | ◐ | ~5400 | 高 | **1.00** |
| L3 模型与图 | ◐ | ◐ 图捕获约束 | ○（下游 torchair） | **● 隐性知识** | **● 静默算错最难查** | ~3000 | 中 | **0.40** |
| L4 数据面传输 | ◐ | ● 通道配对/死锁 | ◐（存储/调度/并行三侧） | ◐ | ● 强度高频率低 | ~1800 活跃（+2057 维护态） | 低-中 | **0.30** |

**结论**：
1. **L2 是最重层**（约为 L1 的 2.2 倍、L4 的 3.3 倍）——纵切把正确性协议集中到 L2 的代价，用"L2 配副手/可拆分性"对冲，不能靠单层硬扛。
2. **L1 与 L3 接近、L4 最轻**——L4 的量里一半是维护态 connector；但注意 L4 的死锁类故障排查强度高，oncall 强度不能按 0.30 线性折算。
3. **L3 的 0.40 不含培养成本**：其知识深度意味着替补上手需要 2-4 周跟班，是四层中"备份最贵"的层。
4. 与横切方案对比：纵切把最重层从 L1（编排+语义混合）换成 L2（纯计算语义），**负载更集中但边界更清**——集中可通过配副手解决，边界模糊（横切时 L1/L2 语义重复）则无法靠加人解决，这是纵切更优的根本原因。
