## Assistant <sup>2026/8/17 17:32:31</sup>

结论先说：**非边云场景下不存在“对端发现”问题**——因为 4 台机器是由同一个分布式启动器(torchrun / ray)一次性拉起、组成**单一 world group** 的，所有子组(DP/PP/EP)的建组都挂在这个世界组唯一的 rendezvous TCPStore 上，IP/端口交换由通信库在 init 阶段经 store 自动完成，不需要 cloud_addr / IP broker 那套机制。

具体链路(对照边云差异)：

**1. 唯一入口：master_addr:master_port 的 TCPStore**

torchrun(或 ray)拉起时把 `MASTER_ADDR`/`MASTER_PORT`/`RANK`/`WORLD_SIZE` 注入每个进程。vLLM 侧在 [parallel_state.py:1642-1645](vllm/vllm/distributed/parallel_state.py#L1642-L1645) 走 `nnodes > 1` 分支：

```python
if parallel_config.nnodes > 1:
    ip = parallel_config.master_addr        # node rank 0(启动节点)
    port = parallel_config.master_port
    distributed_init_method = get_distributed_init_method(ip, port)  # tcp://ip:port
```

pp rank1 的两台服务器上的所有 worker 进程，启动第一件事就是 connect 这个 store,`init_process_group` 建世界组([parallel_state.py:1698](vllm/vllm/distributed/parallel_state.py#L1698))。**它们不需要互相知道 IP,只需要知道 master(node 0)的 IP**,而这是启动器给的。

**2. DP/EP 子组：new_group 复用世界组 store,不做独立 rendezvous**

DP 组、EP 组、PP 组都是 `torch.distributed.new_group`([parallel_state.py:417](vllm/vllm/distributed/parallel_state.py#L417)、[:494](vllm/vllm/distributed/parallel_state.py#L494)、[:1706](vllm/vllm/distributed/parallel_state.py#L1706))。`new_group` 的握手**不新开端口**，而是在世界组的 TCPStore 里用 prefix key 标记“某子组的 rank i 已就位”，全员到齐后由通信库建 communicator。

**3. “知道对端 IP/端口”发生在 HCCL/NCCL/gloo 的 bootstrap 里**

communicator 初始化时，每个 rank 把自己的可达地址写进 store、再从 store 读出其他成员的地址，然后直连。这是 NCCL/HCCL bootstrap 的标准机制(经 store 交换 bootstrap 地址，不走广播)。所以业务代码层面完全感知不到“对端 IP 端口”这件事。

---

**为什么边云场景反而需要 IP-exchange store?**

对比 [passive_core.py:1083-1119](vllm-ascend/vllm_ascend/v1/engine/passive_core.py#L1083-L1119) 的注释：边云的 coord gloo 组**不是** `new_group` 挂在世界组 store 下，而是 `stateless_init_torch_distributed_process_group` 另起一个独立 TCPStore(`master_port+201`)。独立 store 的 rendezvous 必须指定一个“全体成员直连可达”的 host——而 `master_addr` 指向的是边端，云 DP0/DP1 彼此的 IP 无从得知，所以只能让边 DP0 当 IP broker(`master_port+200` 交换 `coord_master_ip`),云 DP1 拿到云 DP0 的 IP 才能 connect。

一句话总结：**边云是“独立 stateless 组 + 独立 TCPStore”所以需要显式换 IP;非边云是“世界组 + new_group 子组”，一切 IP 交换都藏在通信库 bootstrap 里，由启动器注入的 master_addr:master_port 兜底。**

对，但可以拆成两层说更准确——**“要这个组”和“要 IP 交换”是两个原因**：

**1. 组本身：为云侧跨 DP 的 PD 调度协调而设(你说的这层)**

边云 PD batch 分离下，云侧每个 DP rank 是一个**独立的 PassiveEngineCore / PassiveScheduler 进程**(两套 deployment),它们在运行期要互相协调:[passive_scheduler.py:895-1034](vllm-ascend/vllm_ascend/core/passive_scheduler.py#L895-L1034) 里的跨 DP batch_type 协调(MoE 时 EP all-toall 配对前要对齐两边的段类型)和中间层段同步，都走 `dp_coord_group` 这个 gloo 组。边端**不在组里**——它只借出 pp0/pp1 两段，云到云的协调是云侧自己的事。

这个思路其实和上游一致：标准 vLLM 的跨 DP 调度协调也是 stateless 组([stateless_coordinator.py](vllm/vllm/distributed/stateless_coordinator.py)、[parallel.py:619 `stateless_init_dp_group`](vllm/vllm/config/parallel.py#L619)),不挂在世界组下。

**2. IP-exchange store:边云部署形态特有的补丁(这层和你说的原因不同)**

stateless 组的 rendezvous 必须有一个“全体成员直连可达”的 host。上游标准场景这个 host 是现成的——`data_parallel_master_ip`(CLI 传或 dp rank0 充当)。但边云形态下：

- `master_addr` 指向**边端**，不是云 DP0,云 DP 连它建不了云到云的组；
- 云双机的 DP0/DP1 彼此 IP 无从得知，又没有 CLI 参数可传；
- 老实现 `host="127.0.0.1"` 只在同机共置时碰巧能通，双机部署时 DP1 连到自己的回环，rendezvous 永远完不成([passive_core.py:1090-1093](vllm-ascend/vllm_ascend/v1/engine/passive_core.py#L1090-L1093) 的 hang 注释)。

所以才补了“边 DP0 当 IP broker”这个 one-shot store:云 DP0 写 `coord_master_ip`、云 DP1 读出来、然后直连云 DP0 的 `master_port+201`。

所以一句话：**协调需求决定了“必须有云到云的 stateless 组”；边云没有现成 rendezvous 点(上游的 data_parallel_master_ip 在这里不存在)决定了“必须有 IP 交换”**。两者叠加才是你看到的 cloud_addr/IP-exchange 那套机制。

## Assistant <sup>2026/8/17 18:08:52</sup>

三个端口分属**三个完全不同的通信层**，从上到下：

**1. `--port`(默认 8000)—— 用户面，API 服务端口**

[api_server.py:158](vllm/vllm/entrypoints/api_server.py#L158)。纯对外的 HTTP/gRPC 服务入口，客户端请求打到这里。和分布式内部通信无关。(gRPC 入口默认 50051,是另一个独立项。)

**2. `--data-parallel-rpc-port`(默认 29550)—— 控制面，DP 引擎间的 ZMQ 握手/消息端口**

[parallel.py:132](vllm/vllm/config/parallel.py#L132) `data_parallel_rpc_port`,注释 "Port for data parallel messaging"。用途有两处：

- **正常模式**：AsyncLLM(引擎客户端)和各 DP rank 的 EngineCore 子进程做 ZMQ handshake 的 ROUTER socket 端口([v1/engine/utils.py:1165-1166](vllm/vllm/v1/engine/utils.py#L1165-L1166)),`rpc_port or get_open_port()`,0/不给则自动挑；
- **headless/external-LB 模式**：dp rank>0 的节点无头拉起时，回连头节点的地址就是 `data_parallel_master_ip:data_parallel_rpc_port`([serve.py:223-225](vllm/vllm/entrypoints/cli/serve.py#L223-L225))。

它走的是 **ZMQ,不是 torch.distributed**,只做请求分发/引擎管理这类“消息”传递。

**3. `--master-port`(默认 29501)—— 集合通信面，torch.distributed rendezvous store 端口**

[parallel.py:294-297](vllm/vllm/config/parallel.py#L294-L297) `master_addr/master_port`,"distributed master address for multi-node distributed inference"。它是 `init_distributed_environment` 建世界组的 TCPStore(`tcp://master_addr:master_port`,前面看过的 [parallel_state.py:1642-1645](vllm/vllm/distributed/parallel_state.py#L1642-L1645)),所有 HCCL/gloo 的 world 组和 `new_group` 子组 rendezvous 都挂在这上面。

另外在你这个边云代码库里，`master_port` 还兼任**派生端口的基址**：cloud_ip store = `master_port+1+dp`、IP-exchange = `master_port+200`、gloo coord = `master_port+201`、PRE/POST_OUT ZMQ 也按它偏移。所以边云改这个值要小心连锁反应。

**一张表总结：**

| 参数 | 默认 | 协议 | 谁连谁 | 干什么 |
|------|------|------|--------|--------|
| `--port` | 8000 | HTTP/gRPC | 客户端 → API server | 对外推理服务 |
| `--data-parallel-rpc-port` | 29550 | ZMQ | AsyncLLM ↔ 各 DP EngineCore;headless 节点 → 头节点 | 引擎握手、请求分发 |
| `--master-port` | 29501 | TCPStore | 所有 rank → master 节点 store | HCCL/gloo 集合通信 rendezvous(边云下还派生一串内部端口) |

注意还有个易混的 `data_parallel_master_port`(默认 29500,和 `--master-port` 差 1):那是单机 dp>1 时 dp master 组 TCPStore 的端口，和上面三个都不是一回事。

两个概念方向相反：一个是**bind**(我监听在哪)，一个是**advertise**(我告诉同伴我的地址是啥)。

**`--host`:API server 的监听地址，面向用户**

`vllm serve` 的参数，默认 `0.0.0.0`,只决定 HTTP/gRPC 服务 socket bind 到哪个网卡。**不参与任何 vLLM 内部进程间通信**。

**`VLLM_HOST_IP`:本机对内通信的“身份 IP”,面向 vLLM 进程互联**

是 [network_utils.py:33-44](vllm/vllm/utils/network_utils.py#L33-L44) `get_ip()` 的取值来源(优先读它；不设则自动探测网卡 IP,探测失败回落 `0.0.0.0`)。所有“vLLM 进程要把自己的 IP 告诉别的进程”的地方都用它：

- executor 构造 `distributed_init_method`(如 [uniproc_executor.py:73](vllm/vllm/v1/executor/uniproc_executor.py#L73));
- ray 的 `get_node_ip`([ray_utils.py:94](vllm/vllm/v1/executor/ray_utils.py#L94));
- **你这个边云代码库里最关键的两处**：云 PassiveEC 写 `cloud_ip` store 上报给边(passive_core.py `_my_ip = get_ip()`,边据此 connect 云的 ZMQ),以及云 DP0 写 `coord_master_ip` 给云 DP1([passive_core.py:1100-1114](vllm-ascend/vllm_ascend/v1/engine/passive_core.py#L1100-L1114))。

**为什么需要它：多网卡机器的自动探测会选错**

`get_ip()` 不带环境变量时靠 UDP connect 之类的方式探测默认路由 IP,多网卡(比如有管理网 + 业务网，或容器有桥接网卡)时常选到**同伴不可达的那个网段**。后果在边云里很直接：云上报的 `cloud_ip` / `coord_master_ip` 是个边或对端云够不着的 IP,rendezvous/ZMQ connect 卡死。这时必须显式 `export VLLM_HOST_IP=<业务网段IP>`。

**对照表：**

| | `--host` | `VLLM_HOST_IP` |
|---|---|---|
| 层面 | 用户面(API 服务) | 内部通信面(进程互联) |
| 语义 | bind:服务监听在哪 | advertise:我的地址是什么 |
| 默认 | 0.0.0.0(全网卡) | 未设则自动探测网卡 IP |
| 影响范围 | 只有 API server 端口 | distributed init、ZMQ handshake、cloud_ip/coord_master_ip 上报、ray node ip |
| 典型用法 | 一般不动，或 0.0.0.0 | 多网卡机器上必须显式指定可达网段 |

两个常见误区顺带提一下：

1. 把 `--host` 设成具体业务网 IP 以为能解决互通问题——没用，它只管 API 端口监听，内部握手该选错网卡还是选错；
2. `HOST_IP`(无前缀)已被废弃并被**忽略**(Docker 常用它做容器网络交互，[network_utils.py:35-42](vllm/vllm/utils/network_utils.py#L35-L42) 会打 deprecation 警告)，必须用 `VLLM_HOST_IP`。

## 非边云场景(标准 vLLM)

| # | 通道 | 位置 | 用法 |

| 2 | **MessageQueueBroadcaster 的 remote XPUB** | [shm_broadcast.py:424-433](vllm/vllm/distributed/device_communicators/shm_broadcast.py#L424-L433) | 有跨机 reader 时，大对象广播 socket bind 在 `tcp://{get_ip()}:随机端口` |

| 4 | **ray 集群 driver/node IP** | [ray_executor.py:202](vllm/vllm/v1/executor/ray_executor.py#L202)、[ray_utils.py:94](vllm/vllm/v1/executor/ray_utils.py#L94) | ray 初始化时标识本节点 |

## 边云场景

在上述基础上(继承 #1/#2,取决于 executor),**新增三处，且都是致命依赖**：

| # | 通道 | 位置 | 用法 |
|---|------|------|------|
| 1 | **cloud_ip store 上报** | [passive_core.py:1017](vllm-ascend/vllm_ascend/v1/engine/passive_core.py#L1017) | 云 PassiveEC 启动时把 `get_ip()` 写进 `master_port+1+dp` 的 store;边读到后构造 connect 云 ZMQ 的 endpoint。**云多网卡选错 IP → 边到云的 SchedulerOutput 通道永远连不上** |
| 2 | **coord_master_ip 上报** | [passive_core.py:1100-1119](vllm-ascend/vllm_ascend/v1/engine/passive_core.py#L1100-L1119) | 云 DP0 把 `get_ip()` 写入 IP-exchange store(`master_port+200`),云 DP1 读出后 connect `master_port+201` 的 gloo coord 组。**选错 → 云 DP1 连到错误机器的回环/不可达地址，`_create_c10d_store` hang**(就是注释里记录的先例) |
| 3 | **边侧 shared-model executor 的广播 MQ** | [shared_model_multiproc_executor.py:1141](vllm/vllm/v1/executor/shared_model_multiproc_executor.py#L1141) | 边 executor 创建 broadcast MQ 用 `get_ip()` 作 connect_ip(边本机，一般 loopback 也通，风险低) |

## 一句话对比

- **非边云**:`VLLM_HOST_IP` 主要影响**ZMQ 广播通道 bind 地址**(#1/#2)+ ray 场景的 DP 地址(#3);集合通信 rendezvous 由 `--master-addr` 决定，不受它影响。
- **边云**：额外决定**云向边、云向云“自我宣告”的 IP**(cloud_ip / coord_master_ip)。云侧多网卡时这是第一优先要显式设置的变量，选错网段的症状是 ZMQ 连不上或 coord 组 hang,而非集合通信报错。

| 侧 | endpoint | IP 来源 |

## POST_OUT(云 → 边，尾段返回)

| 侧 | endpoint | IP 来源 |
|---|---|---|
| 云 | `tcp://*:{post_out_port}` **bind** | `*` = 云本机全网卡 |
| 边 | `tcp://{cloud_addr}:{post_out_port}` **connect** | **云端 IP**,来自 cloud_ip store 自动发现 |

边侧 [patch_engine_core.py:171-189](vllm-ascend/vllm_ascend/patch/platform/patch_engine_core.py#L171-L189):

```python

post_out = f"tcp://{cloud_addr}:{post_out_port}"
```

而云写入的值就是 `get_ip()`([passive_core.py:1017-1028](vllm-ascend/vllm_ascend/v1/engine/passive_core.py#L1017-L1028))——**即云侧的 `VLLM_HOST_IP`(未设则自动探测网卡 IP)**。

## 小结

```
边 (master_addr, 显式)                      云 (cloud_addr = 云 get_ip(), 即 VLLM_HOST_IP)
 │ bind tcp://*:PRE_OUT  ◄─────SchedulerOutput 首段────  connect tcp://master_addr:PRE_OUT
 │ connect tcp://cloud_addr:POST_OUT ──尾段返回──  bind tcp://*:POST_OUT
```

- **PRE_OUT 通道的 IP = 边端 `--master-addr`**:云端连边，IP 是配置显式给的，不存在“选错网卡”问题；
- **POST_OUT 通道的 IP = 云端 `VLLM_HOST_IP`**:云端 bind 的是 `*` 全网卡没问题，但边 connect 的地址是云上报的 `get_ip()` 结果。云多网卡且 `VLLM_HOST_IP` 没设/设错时，PRE_OUT 正常(云→边方向通)、**POST_OUT 卡死(边→云连不上)**，流量表现为“边发出首段后云收得到、但边永远等不到尾段返回”这类单向不通。

另外注意端口按 `dp_rank*2` 偏移(dp0 用 {pre,post} 基址，dp1 各 +2),双端镜像([patch_engine_core.py:186-187](vllm-ascend/vllm_ascend/patch/platform/patch_engine_core.py#L186-L187) ↔ [passive_core.py:1037-1038](vllm-ascend/vllm_ascend/v1/engine/passive_core.py#L1037-L1038));多实例形态下这套基址还要再叠加 instance 偏移(设计文档 §2.2 的端口撞车问题)。

## 第一问:PRE_OUT 云连边用的 IP

**`master_addr`,即边端 IP**,来自 `--master-addr`(CLI 显式传或 torchrun env),不经任何发现机制。[passive_core.py:1040](vllm-ascend/vllm_ascend/v1/engine/passive_core.py#L1040):


云发起这条 TCP 连接时，源 IP 由云的路由表按“到 master_addr 的路由”自动选网卡。**这个源 IP 恰好就是“云到边方向实际可达的那个网卡 IP”**——这正是你第二问的出发点。

## 第二问：能否从 PRE_OUT 连接直接拿到云 IP,省掉 cloud_ip_store?

**技术上可行，但有代价。** 逐层分析：

### 可行的原理

PRE_OUT 上是云的 PULL 主动 connect 边 bound 的 PUSH,这条 TCP 连接在边侧一定能观察到对端地址：

- **ZMQ SocketMonitor**:边在 bound 的 PUSH socket 上 `get_monitor_socket()`,`ACCEPTED` 事件携带远端 endpoint(`tcp://<云源IP>:<端口>`),pyzmq 原生支持；
- 得到的源 IP 甚至**比 `get_ip()` 更“真”**——它是云→边路由实际选中的网卡，不是探测/环境变量猜的。云多网卡但没设 `VLLM_HOST_IP` 时，这个方案天然不会选错，而现在的 store 方案会把探测错的 `get_ip()` 上报上去(前面讨论过的单向不通问题就不存在了)。

### 但有四个实际代价

1. **时序耦合变深**。cloud_ip_store 的 `get("cloud_ip")` 是一次性 set/get,边阻塞等到值就返回；换成 monitor 方案，边必须等到云的 PULL **真实完成 TCP 握手**才能构造 POST_OUT 的 connect endpoint。阻塞语义差不多，但失败模式变差：云晚起/挂了，store 是干净的 timeout 报错，monitor 是自定义等待循环 + 无区分度的超时。

2. **丢失显式覆盖能力**。现在运维可以 `VLLM_HOST_IP` 强行指定上报 IP(NAT、overlay 网络下源 IP 未必是回连可达地址，比如容器 SNAT 后边看到的源是宿主/网桥 IP,而云真正该被连的是业务平面 IP)。源地址发现绕过了这个人控开关，反而引入新的部署限制。

3. **pyzmq 拿对端地址不直接**。bound PUSH socket 没有“列出已连 peer”的同步 API,只能挂 monitor 收异步事件，还要处理重连(云断线重连源 IP 可能变)、多 dp_rank 时按端口区分对端(`master_port+1+dp` 的配对语义要靠“谁连了这个端口”隐式维护)。cloud_ip_store 的 per-dp 配对是显式的、自解释的。

4. **与既有模式/规划的一致性**。cloud_ip 握手刻意镜像了 IP-exchange store 的 set/get 语义(代码注释原话 "mirroring the existing cloud_ip handshake"),多实例方案的端口/instance 偏移设计(文档 §2.2)也是围绕 store 体系规划的；换成连接派生发现，这套偏移设计要重新推。

### 结论

- **能不能**：能，monitor `ACCEPTED` 事件即可，且对“多网卡选错”这个最大痛点反而更鲁棒；
- **该不该**：不建议整体替换。当前 store 方案的价值在**确定性**(显式 handshake + `VLLM_HOST_IP` 可控 + 干净超时)。如果想借它的优点，更稳的做法是**把 monitor 发现当兜底**：store `get` 到的 cloud_addr 连不通 POST_OUT 时，回落到从 PRE_OUT 连接观察到的源 IP 重试，并打 warning——这样既保留显式控制，又消掉探测选错的静默故障。

PP 并行下(多机 mp backend),`--master-addr`/`--master-port` 定义的是**整个 dp 组的 rendezvous 点**：leader 节点(`node_rank==0`,即 pp 第一段的节点)上的一对 `IP:port`,所有其他节点的角色都围绕它。具体作用按场景分：

## 非边云 PP 多机

**1. torch.distributed 世界组 rendezvous store(核心作用)**

[parallel_state.py:1641-1645](vllm/vllm/distributed/parallel_state.py#L1641-L1645),`nnodes > 1` 时：

```python
ip = parallel_config.master_addr
port = parallel_config.master_port
distributed_init_method = get_distributed_init_method(ip, port)  # tcp://ip:port
```

leader 节点在 `master_addr:master_port` host 一个 TCPStore,pp rank1 机器上的所有 worker 进程 connect 它完成 `init_process_group`。之后的 **PP 子组、组内 TP 子组**都是 `new_group`,rendezvous 复用这同一个 store(prefix key 区分)，HCCL/gloo 的 bootstrap 地址交换也在里面完成。**这就是 pp rank1 机器能“找到”pp rank0 机器的全部机制**--没有服务发现，就这一个静态配置的 store。

**2. headless 工作节点的入口**

非 leader 节点拉起时以 headless 模式进入，日志直白地展示用途([serve.py:206-217](vllm/vllm/entrypoints/cli/serve.py#L206-L217)):

```
Launching vLLM headless multiproc executor,
with head node address {master_addr}:{master_port} for torch.distributed process group.
```

**3. 注意：单机内 worker 的分布式 init 不用它**

每台机器自己 executor 内部给本地 worker 的 `distributed_init_method` 用的是**loopback + 随机端口**([multiproc_executor.py:128-131](vllm/vllm/v1/executor/multiproc_executor.py#L128-L131)),跟 `master_addr` 无关;`master_addr:master_port` 只承担**跨机**那层。

## 边云 PP(你打开的这个文件所在体系)

`master_addr` 恒指**边端**，除了上述世界组作用外，还是一串通道的锚点：

| 用途 | 地址 | 方向 |
|---|---|---|
| PD 世界组 TCPStore(HCCL rendezvous) | `master_addr:master_port` | 云 connect 边 host |
| cloud_ip store(云上报 IP) | `master_addr:master_port+1+dp` | 云 connect 边 host |
| PRE_OUT ZMQ(云收边首段) | `master_addr:pre_out_port+dp*2` | 云 connect 边 bind([passive_core.py:1040](vllm-ascend/vllm_ascend/v1/engine/passive_core.py#L1040)) |
| IP-exchange store(云 DP0 宣告 IP) | `master_addr:master_port+200` | 云 connect 边 host |
| rpc_broadcast_mq(collective_rpc 广播) | 边 leader 侧 | 云 connect 边 |

即边云下 **`master_port` 是“基址 + 一堆派生偏移”**(+1+dp / +200 / +201),改它要整组一起改。

## 使用要点

- 所有节点的拉起命令必须传**同一对** `--master-addr/--master-port`,`master_addr` 填 **leader 节点(非边云)/ 边端(边云)的可达业务网 IP**,配合各自 `--node-rank`;torchrun 拉起时对应 `MASTER_ADDR`/`MASTER_PORT` env 自动注入；
- 单机 PP(不管 pp 几)根本不跨机，保持默认 `127.0.0.1:29501` 即可，不会被用到跨机路径；
- 它和之前聊的 `VLLM_HOST_IP` 的分工:`master_addr` 是“**大家去连谁**”(leader 侧地址，显式配置);`VLLM_HOST_IP` 是“**我自我宣告的 IP**”(leader 侧 ZMQ bind 用 `get_ip()`,边云下云上报也用它)。多网卡机器上 leader 节点两个都要设对:`master_addr` 错了所有 worker 连不上 store,`VLLM_HOST_IP` 错了 ZMQ 广播/上报通道选错网卡。

**是的--在“世界组 + new_group 子组”这条路径上，gloo 和 HCCL 共用同一个 `master_addr:master_port`,和后端无关。** 但要把 rendezvous 面和数据面分开，另外有几个例外。

## 为什么共用

`--master-addr/--master-port` 定义的是一个 **TCPStore**(纯 TCP,libtcp 实现，本身没有任何 gloo/HCCL 色彩)。`init_process_group(backend=..., init_method="tcp://master_addr:master_port")` 的逻辑是：

1. rank 0 host 这个 store,其余 rank connect,得到**同一个 store 句柄**；
2. 之后无论 `new_group` 建的是 HCCL 组还是 gloo 组，都从主 store 派生一个 **PrefixStore**(同一个 IP:port,只是 key 加前缀，如 `tp_group/`、`pp_group/`、`cpu_group/`)；
3. **通信库 bootstrap 阶段**：每个 rank 把自己数据面的地址写进这个 prefix store,再读出同伴的地址，然后建立直连。

所以 gloo 组和 HCCL 组的**握手流量走的是同一对 `master_addr:master_port`**,只是 key 前缀不同。典型例子:[parallel_state.py:1706](vllm/vllm/distributed/parallel_state.py#L1706) 的 `tp_pp_cpu_group` 是 gloo,设备组是 HCCL,两者都从世界组 store 派生。

## 但数据面不走它

bootstrap 完成后，实际 allreduce/allgather 是 rank 之间的**直连 socket/RDMA**(地址是第 3 步经 store 交换的)，`master_addr:master_port` 只在启动期用一次，不承载任何训练/推理通信。

## 例外：stateless 组不用 `--master-port`

这个代码库里有几类组**绕开了**世界组 store、自己另起炉灶：

| 组 | rendezvous 地址 | 用不用 `--master-addr/--master-port` |
|---|---|---|
| 边云 gloo coord 组 | 云 DP0 的 IP:`master_port+201` | **不用**作 store;IP 经 IP-exchange store(`master_addr:master_port+200`)交换，即 master_addr 用于“发现”但 store 端口是 +200/+201 |
| 标准 stateless DP 组([parallel.py:619](vllm/vllm/config/parallel.py#L619)) | `data_parallel_master_ip:动态端口` | 完全不用 |
| 单机多进程本地组([multiproc_executor.py:129](vllm/vllm/v1/executor/multiproc_executor.py#L129)) | `127.0.0.1:随机端口` | 完全不用 |

## 一句话总结

- **凡是通过 `init_process_group` + `new_group` 建的组**(世界组、TP/PP/DP/EP 子组、gloo CPU 组、HCCL 设备组):全部 rendezvous 于 `--master-addr:--master-port`,后端无关；
- **凡是 `stateless_init_*` 建的组**(边云 coord 组、标准 DP 协调组)：自带独立 store,用自己的端口(coord 是 `master_port+201`,借了 master_port 的基址但不是同一个 store);
- 两种后端的区别只在数据面直连用什么库，握手面是同一套 TCPStore 机制。
