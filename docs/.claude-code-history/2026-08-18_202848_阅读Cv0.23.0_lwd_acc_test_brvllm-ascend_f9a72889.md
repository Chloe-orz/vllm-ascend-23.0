- API server 与云实例**无对应关系**：PRE_OUT/POST_OUT 是 EngineCore↔云通道，API server 层完全不感知实例。

### 关键缺口（现有机制不直接满足的部分）

1. **“N 个端点”不成立**：`run_multi_api_server` 的 N 个 ApiServer 子进程**共享同一个 HTTP listen socket**（`v1/utils.py:343-351` 传 sock）——对外是 1 个 IP:port，N 个进程只是 accept 并发分摊。`client_index` 按进程区分，仅用于输出回投，客户端无法按端点选实例。若要“端点 i → 实例 i”，需要改造（多端口可参考 `dp_supervisor.py` 的 multi-port 形态，但那是 per-DP-rank 端口，非 per-instance）。
2. **请求不带实例信息**：现有请求元数据无 instance_id 字段；若要 §1.4 遗留的“api 按 KV 选实例”，需新增请求头/hint 透传到 EngineCore + 前端有 per-instance KV 视图（即文档 §3.5 InstanceLoadStats 前端发布，文档已列为后续最大改动之一）。
3. 互斥项：`--api-server-count` 与 `--headless`、Rust frontend、elastic EP 互斥/被钳制（`serve.py:123-137`）；边侧非 headless，无冲突。
4. 实现期核实项：dp=1 + `api_server_count=N` 时 DPCoordinator 是否仍被 spawn（dp=1 无 coordinator 语义，预计跳过，需跑通确认）。

### 建议（v1 口径）

- **v1 用“1 个端点 + EngineCore 内调度”**：甚至不需要 N 个 API server——单 API server（或沿用 D 个）+ 文档 §3.4 leader 决策实例即可完整复用边侧算力，多实例收益落点在 EngineCore 层不在前端层数量。

## 1. “共享同一个 listen socket”是什么意思

启动链（[serve.py:284](vllm/vllm/entrypoints/cli/serve.py#L284) / [serve.py:343-352](vllm/vllm/entrypoints/cli/serve.py#L343-L352)）：

```
launcher 进程（run_multi_api_server）
  ① listen_address, sock = setup_server(args)     ← 只创建【一个】监听 socket，
                                                      bind host:port + listen，一次
  ② spawn ApiServer_0 .. ApiServer_{N-1}
       APIServerProcessManager(..., sock=sock, ...)   ← 同一个 socket（fd）传给每个子进程
```

关键在 [utils.py:229-235](vllm/vllm/v1/utils.py#L229-L235)：每个子进程的 spawn 参数都是**同一个 `sock` 对象**（spawn 语义下是同一个 fd 的拷贝）。每个子进程拿到后用 uvicorn 以 `sock=sock` 方式启动 HTTP 服务（[api_server.py:683-685](vllm/vllm/entrypoints/openai/api_server.py#L683-L685) `build_and_serve(..., sock=sock)`）。

```
                          同一个 listen socket fd（内核中只有一份 bind :8000）
                                   │
        ┌──────────────────────────┼──────────────────────────┐
        ▼                          ▼                          ▼
   ApiServer_0                ApiServer_1  ...           ApiServer_{N-1}
   accept() 阻塞              accept() 阻塞               accept() 阻塞
```

这就是 nginx 多 worker 的模式：**N 个进程同时 accept 同一个端口**，一条新 TCP 连接到来时，内核把它交给当时正好在 accept 的某一个进程。所以：

- 对外客户端视角：只有**一个** `host:port`。客户端没有任何办法指定“我要连第 3 个 API server 进程”--连接落给哪个进程是内核调度决定的，与请求内容、来源都无关。
- N 个进程的作用仅仅是**分摊 HTTP 并发连接**（每个进程单线程 uvloop，N 个进程扛 N 倍连接数），不是提供 N 个入口。

## 2. client_index 到底是什么

每个子进程出生时带一份 `client_config`（[utils.py:214-219](vllm/vllm/v1/utils.py#L214-L219)）：

```python
client_config = {
    "input_address": in_addr,      # 本进程自己的 ZMQ ROUTER 地址
    "output_address": out_addr,    # 本进程自己的 ZMQ PULL 地址
    "client_count": num_servers,   # N
    "client_index": i,             # 我是几号前端进程
}
```

然后形成这样的通道（EngineCore 侧，[core.py:1492-1499](vllm/vllm/v1/engine/core.py#L1492-L1499) / [1590-1595](vllm/vllm/v1/engine/core.py#L1590-L1595)）：

```
ApiServer_0 ─ input ROUTER  addr_0 ◄─DEALER─ ┐
ApiServer_1 ─ input ROUTER  addr_1 ◄─DEALER─ ├─ EngineCore（input_queue 汇成一锅）
ApiServer_2 ─ input ROUTER  addr_2 ◄─DEALER─ ┘
ApiServer_i ─ output PULL   out_i  ◄──PUSH─── EngineCore（N 条，按 client_index 选一条）
```

请求方向：前端发请求时**盖上自己的编号**（`client_index=i`，[core_client.py:1097](vllm/vllm/v1/engine/core_client.py#L1097)），所有请求进 EngineCore 的同一个 `input_queue`。

输出方向（[core.py:1614-1630](vllm/vllm/v1/engine/core.py#L1614-L1630)）：

```python
client_index, outputs = output
...
sockets[client_index].send_multipart(...)   # 只发给"发起请求的那个前端进程"
```

**client_index 存在的唯一理由是回信地址**：HTTP 连接是被某个 ApiServer 进程 accept 的，这个进程持有该连接的 SSE/streaming 上下文；token 流必须送回同一个进程才能写回 HTTP 响应。所以 EngineCore 要知道“这条输出该从 N 条 PUSH 里挑哪一条”。

## 3. 为什么这不能当“端点 i ↔ 实例 i”用

三个错位叠在一起：

| 层 | 现实 | 需要的样子 |
|---|---|---|
| **端口层** | N 个进程共用 1 个端口，客户端只有一个地址可连，“第 i 个端点”根本不存在 | N 个不同端口 `:8000+i`，客户端连哪个端口 = 选哪个实例 |
| **进程↔请求** | 哪条连接被哪个进程 accept 是**内核随机分配**的；就算你想做 “client_index=i 的进程发的请求都 pin 实例 i”，请求也会随机落在任意进程上 | 请求能确定性地带上实例信息 |
| **client_index↔instance** | client_index 是“前端进程编号”（回信地址），请求元数据里没有 instance_id；EngineCore 内的实例选择是另一个正交维度（文档 §3.4 的 InstanceDispatcher，leader 在 EngineCore 里决策） | 请求携带 instance_id 透传到调度层 |

换个说法：**client_index 回答“输出送回哪个前端进程”，不回答“这个请求去哪个云实例”**。一个是回程路由，一个是调度决策，两者在现有代码里没有任何绑定，也不该绑定--internal LB 下 EngineCore 选前端是“谁发的回谁”，选 DP rank 是按负载（`get_core_engine_for_request`，[core_client.py:1398-1426](vllm/vllm/v1/engine/core_client.py#L1398-L1426)），从来就没有 instance 这个维度。

一个具体反例：假设你魔改出“client_index=i 的请求固定去实例 i”。客户端 A 连上端口 8000，这条连接被 ApiServer_2 接走（内核随机），于是 A 的所有请求都被 pin 到实例 2--而 A 本意可能是想用实例 0。**端点语义在 accept 随机性面前直接失效**。

## 4. 如果真要“端点/KV 选实例”，改造点在哪

| 路线 | 改动 | 语义 |
|---|---|---|
| **a. 多端口** | 每个子进程独立 bind 自己的 `host:port_i`（不走共享 sock，参考 [dp_supervisor.py](vllm/vllm/entrypoints/openai/dp_supervisor.py) 的先例，但它是 per-DP-rank 端口）+ 请求带 `instance_id = client_index` 静态映射 | 端点 i 硬绑定实例 i；丧失跨实例负载均衡，与文档 §3.3 least-loaded 相悖 |
| **b. 单端点 + 请求头** | 保持单端口，客户端在 HTTP header（如 `x-instance-id`）里带实例提示，透传进请求元数据到 EngineCore，InstanceDispatcher 优先尊重 hint、无 hint 时 fallback least-loaded | “api 基于 kv 选择”（§1.4 问题 1）的自然落点：选择逻辑在客户端/路由层，边侧只透传 |
| **c. 单端点 + 引擎决策**（文档已定） | 零前端改动，leader EngineCore 统一 InstanceDispatcher | 端点数与实例数完全解耦，v1 推荐 |

需要注意：路线 a/b 都要动请求元数据结构（`EngineCoreRequest` 加 instance 字段）+ 文档 §3.5 的 per-instance 负载/KV 视图发布（否则客户端没法“基于 KV 选”），这是同一个特性的两半。

这个模型和文档高度兼容：文档 §3.3 本来就是“请求 pin 实例后 draft/prefill/MTP/decode 全跟随”，只是 pin 的决策者从 EngineCore 里的 InstanceDispatcher（§3.4 方案 c）**上移到网关**。端点 i = 实例 i = client_index i，三个编号天然合一。

## 一个重要的“白嫖”发现

请求**已经**携带 client_index 到 EngineCore（[core_client.py:1097](vllm/v1/engine/core_client.py#L1097)，本用于输出回投），EngineCore 产出的 token 流已经按 client_index 定向送回发起端点（[core.py:1630](vllm/v1/engine/core.py#L1630)）。所以“网关选端点 → 请求带实例 → 输出回同端点”这条链的**传输层全部现成**，缺的只有两件事：①每个子进程独立端口；②EngineCore 把 client_index 当 instance_id 用。

## 修改点（按层）

### 改动 1：HTTP 监听层——每子进程独立 bind（核心改动）

| 位置 | 现状 | 修改 |
|---|---|---|
| [serve.py:284](vllm/vllm/entrypoints/cli/serve.py#L284) | `setup_server(args)` 创建 **1 个** sock | 新形态下创建 N 个 sock_i（各 bind `host:base_port+i`，或显式端口列表——建议与文档 §2.2 `pre_out_ports` 同口径**显式配置**） |

### 改动 2：instance_id 语义（EngineCore/scheduler 层）

- 请求 admission 时 `instance_id = client_index`（dp=1 边云多实例形态下），路由到第 instance_id 个 per-instance scheduler（即文档 §3.1 的 N 个 scheduler 分组，只是构造来源从 InstanceDispatcher 分发变为请求自带）

- **§5.1 调度完全不动**：pin 只决定请求去哪个实例的队列（亲和），何时下发 HEAD 仍由 leader 的 arrival-FIFO/水位状态机决定；TAIL 的 RecvReadyFirst 也不受影响

### 改动 3：网关的均衡反馈（可分级）

### 零改动清单（评审时明确排除）

- ZMQ input/output 全套：每子进程 ROUTER/PULL、地址 pipe 回传、handshake、EngineCore DEALER×N/PUSH×N——零改

## 关键风险

1. **网关 LB 粒度**：SSE/HTTP keep-alive 长连接会粘住一个端点 → 负载倾斜。网关必须请求级分发（短连接或 LB 支持 request/stream 级路由），否则“均衡选择实例”失效。这是部署约束，要写进文档。
2. **端点级故障语义**：ApiServer_i 进程挂 → launcher 的 `wait_for_completion_or_failure` 拉停全部（v1“任一挂整体挂”，与实例故障模型一致）；网关摘端点 i 只救流量不救服务。
3. **长连接 + 实例容量**：端点 i 对应实例 i 的 KV/队列是硬隔离的（文档 §6.1 分区），网关若不感知负载，长序列大户粘在端点 i 会打满该实例 edge/N 配额而其他实例闲置（文档 §6.3 已预警的配额匹配问题，在前端 pin 模式下更需要改动 3 的反馈环）。
4. **chunked prefill 保序**：请求已 pin、不迁移，续 chunk 天然同实例（文档 §5.1.3 硬约束 #1 自动满足）。

“前端 internal LB”是上游 vLLM 的一个现成机制，指 **dp>1 且不开 external_lb 时，请求该发给哪个 EngineCore（哪个 dp rank）的选择逻辑，做在 API server 进程内部**（"internal" = vLLM 自己做均衡，区别于 external_lb 把均衡交给外部网关/设备）。具体由三个部件组成：

## 组成

**① 决策者：`DPLBAsyncMPClient`（每个 ApiServer 进程内一个）**

[core_client.py:1365](vllm/v1/engine/core_client.py#L1365)，类注释就是 "Load-balances between multiple engine processes"。dp>1 internal LB 时工厂创建它（[core_client.py:108-131](vllm/v1/engine/core_client.py#L108-L131)），它持有 D 个 EngineCore 的客户端句柄（`core_engines`），请求到来时调 `get_core_engine_for_request` 选一个发：

```python
# core_client.py:1398-1426（节选）
current_counts = self.lb_engines            # 每引擎 [waiting, running]
for i in range(num_engines):
    idx = (self.eng_start_index + i) % num_engines   # 从自己的起始位开始扫
    waiting, running = current_counts[idx]
    score = waiting * 4 + running            # 排队权重 ×4 + 在跑数
    if score < min_score: ...
current_counts[eng_index][0] += self.client_count   # 本地先 +1 防止两次统计间隔内扎堆
chosen_engine = self.core_engines[eng_index]
```

打分就一条公式：**`waiting×4 + running` 最小的 EngineCore 胜出**（排队请求权重是 4，惩罚排队长的引擎）。`eng_start_index` 按本进程的 client_index 偏移起始扫描位，保证 D 个引擎全空时多个 ApiServer 不会一窝蜂全选 dp0。

**② 统计源：`DPCoordinator` 独立进程**

launcher 额外 spawn 的一个小进程（[coordinator.py:23](vllm/v1/engine/coordinator.py#L23)，边云 dp=2 现网就有它）。每个 EngineCore 周期性把自己 scheduler 的 `[waiting, running]` 计数发给它，它聚合后 **XPUB 广播**；每个 ApiServer 的后台任务用 XSUB 订阅（[core_client.py:1236-1348](vllm/v1/engine/core_client.py#L1236-L1348)），约每 100ms 刷新一次本进程的 `lb_engines` 表。这就是前端做均衡的“眼睛”。

**③ 发送通道：与前面讲的 ZMQ 拓扑是同一套**

每个 EngineCore 以 `DEALER(identity=dp_rank)` 连到 ApiServer 的 input ROUTER；LB 决策后按 identity 定向发给选中的那个 EngineCore（[core_client.py:1348-1351](vllm/v1/engine/core_client.py#L1348-L1351) 请求同时盖上 `client_index` 用于输出回投；abort 用 `reqs_in_flight` 表找回原引擎）。

## 场景四：dp=2 两实例（N=2, D=2）—— “端点定实例、负载定 dp”扩展形态

```
                 API 网关（请求级分发，选端点 = 选实例 pin）

   │   lb_engines=[[w,r],[w,r]] ← XSUB ← DPCoordinator ×1（XPUB）
   │   选 dp：score = waiting×4 + running 最小     ← dp 维度：前端 internal LB（零改）
   │ bind ROUTER/PULL
   ▼（DEALER id=dp_rank 定向，请求带 ci）
   ┌─────────────┐          ┌─────────────┐
   │ EngineCore_0│          │ EngineCore_1│   ← 仍是 D=2 个（N 不加进程）
   │  (dp0)      │          │  (dp1)      │

   │ ├ inst0 组  │          │ ├ inst0 组  │   ← 每 EC 内 N=2 组，全局 N×D=4
   │ └ inst1 组  │          │ └ inst1 组  │
   │ §3.4 all_reduce (instance_id+bt)：2DP 同 (实例,bt) 配对 │
   └──────┬──────┘          └──────┬──────┘
          └───── 双 dp 共享 worker ×1（shared-model）─────┘
          │ PRE_OUT：边 dpX ──► 云 (实例i, dpX)
   ┌──────┴───────────────┬──────────────────┐
   ▼                      ▼                  ▼

          │
   输出 sockets[ci] 回投：回端点 i（与落哪个 dp 无关）
```

**选择逻辑（两个正交维度各归各）**：
1. **实例维度 = 网关**：选端点 i -> 请求带 `ci=i` -> 落进任一 EngineCore 后都路由到实例 i 的 scheduler 组（请求 pin 后 draft/prefill/MTP/decode 全跟随）；
2. **dp 维度 = 前端 internal LB**：ApiServer_i 按 `waiting×4+running` 在 dp0/dp1 两个 EngineCore 间选，**不做端点↔dp 静态绑定**（2DP 是 EP all-toall 紧耦合，静态分割流量会导致两侧失衡）；
3. **下发时机** = EngineCore 内 §3.4（leader 提议 + all_reduce 分发 `(instance_id, bt)`，2DP 同实例同 bt 配对云 EP）+ §5.1 水位；
4. 输出回投只看 ci：哪个端点进的请求回哪个端点，与它被调度到哪个 dp/实例无关。

**进程清单**：ApiServer×2（双端点）、EngineCore×2、worker×1、DPCoordinator×1、云 PassiveEC×4。
